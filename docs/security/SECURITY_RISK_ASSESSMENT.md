# Relay 公网部署安全风险评估与整改清单

## 1. 文档目的

本文记录 `remote-assist-tool` Relay 暴露到公网前必须处理的安全风险，供后续整改、复核和上线评审使用。

本文不是部署操作手册，也不表示当前版本已经满足生产安全要求。所有 P0、P1 风险在修复、验证或完成正式风险接受前，Relay 不应作为正式公网服务开放。

## 3. 目标部署拓扑

```text
公网 Share / Help
        |
        | TLS 1.3, jk-sg.iflyedusvc.com:8443
        v
      ELB
        |
        | 私网明文 TCP 8443
        v
  Relay 私网后端

公网 Share / Help
        |
        | UDP 3478
        v
      ELB
        |
        | 私网 UDP 3478
        v
  STUN / UDP Relay
```

部署约束：

- 公网客户端必须使用 `--insecure=false`，不得使用 `--plain` 或 `--no-auth`。
- Relay 后端只有在 ELB 已终止 TLS，且安全组仅允许 ELB 来源访问时，才允许使用 `--plain`。
- 后端 TCP 8443 和 UDP 3478 不得直接暴露到公网。
- 首次安全上线建议仅开放 TCP 8443，并通过 `--stun ""` 禁用 UDP 3478，直至 UDP 风险完成整改和压测。

## 4. 威胁模型

### 4.1 需要保护的资产

- 被协助终端上的文件、日志、凭据和系统配置。
- 被协助终端上的管理员命令执行能力。
- 协助码、会话密钥和会话标识。
- Relay 主机及其所在 VPC 内的其他服务。
- 审计日志中的终端标识、IP、操作记录和会话元数据。
- Relay 和 ELB 的可用性、带宽、内存与文件描述符。

### 4.2 攻击者能力

- 可以从公网持续连接 TCP 8443，并发送任意协议消息。
- 可以向 UDP 3478 发送任意报文，且可能伪造 UDP 源地址。
- 可以高频尝试协助码、创建伪造 Share 或消耗服务端资源。
- 可能获取日志平台、Relay 低权限账号或 Relay 进程控制权。
- 可能位于同一 VPC，尝试绕过 ELB 直连明文后端。
- 不假设攻击者已经控制被协助终端本地用户界面或 DMS 管理账号。

### 4.3 必须明确的信任决策

需要在整改开始前确认以下问题：

1. Relay 是否属于可信数据边界？
2. 是否要求“Relay 主机或 Relay 进程失陷后，攻击者仍无法解密工具数据或冒充 Help”？
3. UDP P2P 是否为首期上线的必要能力？
4. 是否使用独立 Relay 云主机，还是与现有 DMS、CSB、AppStore、EMQX 混部？

如果第 2 项答案为“是”，当前握手方案不满足要求，必须进行端到端密钥协商改造，不能仅依靠 ELB、systemd 或低权限用户补偿。

## 5. 已有安全控制

当前源码已经具备以下基础控制，但它们不能覆盖后续列出的风险：

- 协助码由 `crypto/rand` 生成，默认使用 54 字符集的 10 位随机码，约 57.5 bit 熵。
- 协助码默认 30 分钟过期，同一会话最多允许一个 Help。
- 公网 TLS 客户端最低版本为 TLS 1.3。
- 单条 TCP 消息限制为 4 MiB。
- TCP 读空闲超时为 2 分钟，单次写超时为 30 秒。
- TCP 全局并发连接上限为 2000，单源 IP 并发连接上限为 128。
- 工具请求和响应使用 XChaCha20-Poly1305 AEAD 加密。
- 管家集成方案要求本地用户确认后才启动 Share。
- 正式部署方案计划使用低权限用户和 systemd 文件系统隔离。

## 6. 风险清单

### SR-001：单连接可重复注册并无限创建会话

- 严重级别：P0
- 状态：OPEN
- 类型：未授权资源耗尽、内存 DoS、日志 DoS
- 代码位置：`internal/relay/server.go:269-279`、`internal/relay/server.go:315-359`、`internal/relay/session.go:81-100`

证据：

- `handleMessage` 收到每个 `MsgRegisterRequest` 都会调用 `handleRegister`。
- `client.Type == ""` 只限制身份字段写入，没有拒绝第二次注册。
- 攻击者首次使用空 `ClientID` 后，可以在同一 TCP 连接上重复注册。
- 每次注册都会生成新协助码并向 `SessionManager` 增加会话。
- 并发连接上限无法限制单连接内的重复注册。
- 非活跃会话最长保留到 TTL 清理周期，期间持续占用内存并写审计日志。

影响：

- 无需猜中协助码即可持续增加会话、日志和内存占用。
- 单个连接可以绕过每 IP 128 并发连接限制。
- 在内存余量较小的混部主机上可能导致 Relay 或其他业务被 OOM Killer 终止。

整改要求：

- 为每条 TCP 连接实现明确状态机：`new -> share` 或 `new -> help`，首个有效业务消息后禁止改变角色。
- 第二次 register 或 join 必须返回协议错误并立即关闭连接。
- 增加全局活跃会话上限、每 IP 活跃会话上限和会话创建速率限制。
- 会话创建失败时不得写入部分状态。
- 连接断开时必须清理该连接关联的全部会话，不得只清理第一条。

验收标准：

- 单连接连续发送两次 register，第二次被拒绝且连接关闭。
- 重复 register 不增加 `GetActiveSessions()`。
- 并发和持续压测期间会话数、内存和日志增长保持在配置上限内。
- 增加覆盖空 `ClientID`、重复 ClientID、register 后 join、join 后 register 的单元测试和集成测试。

### SR-002：UDP 3478 无鉴权、无限 goroutine 和无限中继状态

- 严重级别：P0
- 状态：OPEN
- 类型：UDP Flood、内存 DoS、日志 DoS、反射流量、带宽滥用
- 代码位置：`internal/p2p/stun_server.go:77-97`、`internal/p2p/stun_server.go:101-133`、`internal/p2p/stun_server.go:200-278`

证据：

- 每个非中继 UDP 报文都会启动一个 goroutine 解析 STUN。
- STUN Binding Request 不要求凭据，这是标准 STUN 的常见行为，但当前没有每 IP 或全局 PPS 限制。
- 无效 UDP 报文会写日志，攻击者可放大磁盘和 journal 压力。
- 自定义 UDP 中继接受任意 `sessionID`，不校验它是否属于已认证的 TCP 会话。
- 任意新 `sessionID` 都会在 `relaySessions` 中创建一条保留 5 分钟的记录。
- `relaySessions` 没有总量、每 IP 数量或内存上限。
- UDP 中继没有用户级流量配额或出口带宽上限。

影响：

- 公网攻击者可以制造大量 goroutine、内存状态和日志。
- 伪造源地址的 UDP 请求可能使服务参与反射流量。
- 中继功能可能被滥用为未经授权的 UDP 转发资源。
- UDP 出口带宽耗尽时会影响 TCP Relay 和同机业务。

整改要求：

- 首期上线使用 `--stun ""` 禁用 UDP 3478。
- 使用固定 worker pool，禁止每个 UDP 包创建无上限 goroutine。
- 增加每 IP 和全局 UDP PPS token bucket，并在 ELB/云防火墙配置 UDP PPS 与带宽上限。
- 对无效包日志采样，不得逐包写日志。
- UDP 中继必须使用与已认证 TCP 会话绑定的不可伪造短期令牌，不能仅凭任意字符串 session ID 创建状态。
- 增加中继会话总量、每 IP 数量、单会话带宽和全局带宽限制。
- 对 STUN 请求与响应大小做放大倍率测试。

验收标准：

- UDP 伪造 session ID 不能创建中继状态。
- 超过 PPS、状态数或带宽阈值时稳定丢包，内存和 goroutine 数保持有界。
- 10 分钟 UDP Flood 压测后 TCP 8443 仍能正常注册和建立会话。
- 日志量受采样阈值约束，不随攻击包数量线性增长。

### SR-003：协助码 Join 缺少应用层爆破限制

- 严重级别：P1
- 状态：OPEN
- 类型：凭据爆破、连接 DoS、日志 DoS
- 代码位置：`internal/relay/server.go:363-374`、`internal/relay/session.go:158-188`

证据：

- Join 只进行协助码查表、过期和已连接检查。
- 同一连接可以无限发送错误 Join。
- 没有每 IP、每连接或全局失败速率限制。
- 当前连接限制只约束并发连接，不约束单位时间尝试次数。

风险判断：

- 10 位随机码的在线随机猜中概率很低，爆破成功不是当前最容易的攻击路径。
- 缺少限速仍会造成 CPU、连接和日志压力。
- 协助码泄露后的风险远高于纯随机爆破，因为任何持有码者都能直接接管会话。

整改要求：

- 增加每连接、每源 IP 和全局 Join 尝试 token bucket。
- 单连接连续失败达到较小阈值后立即关闭。
- 不建议只按协助码锁定，否则攻击者可故意锁死合法会话。
- ELB 若进行 SNAT，必须在应用限流前解决真实源 IP 识别问题。
- 对高频失败、分布式低频失败和单码集中尝试建立监控告警。

验收标准：

- 超过阈值的请求被限速或断开，合法低频连接不受影响。
- ELB 场景下多个真实客户端不会被错误聚合为同一个限流主体。
- 失败响应不泄露不必要的会话状态。

### SR-004：审计日志和运行日志记录完整协助码

- 严重级别：P1
- 状态：OPEN
- 类型：敏感凭据泄露、会话接管
- 代码位置：`internal/logger/audit.go:117-123`、`internal/relay/server.go:326-350`

证据：

- `LogCodeGenerated` 把完整 `code` 写入审计日志 Details。
- Relay 普通日志也打印格式化后的完整协助码。
- 协助码是 bearer credential，持有码者不需要额外操作员身份即可尝试 Join。

影响：

- Relay 主机管理员、日志平台账号或日志采集链路失陷后，可在有效期内接管被协助终端。
- 日志备份会延长本应只有 30 分钟有效期的敏感数据留存时间。

整改要求：

- 审计日志和运行日志禁止记录完整协助码。
- 仅记录不可逆指纹，例如带服务端独立审计密钥的 HMAC 截断值；不得直接使用无密钥 SHA-256 代替。
- 普通排障日志最多显示固定长度掩码。
- 日志平台设置最小权限、保留周期和访问审计。
- 现有历史日志按公司敏感数据处理流程评估和清理。

验收标准：

- 全仓搜索及端到端日志采集均不能找到完整协助码。
- 同一会话仍可通过稳定指纹关联注册、Join、关闭和告警事件。
- 测试覆盖日志、journal、审计文件和错误输出。

### SR-005：当前工具通道加密不能抵抗恶意或失陷的 Relay

- 严重级别：P1
- 状态：OPEN，需要架构决策
- 类型：数据泄露、命令伪造、会话接管、安全能力描述不准确
- 代码位置：`internal/proto/handshake.go:33-41`、`internal/client/help_mcp.go:34-52`、`internal/client/share.go:690-706`、`internal/relay/server.go:307-310`

证据：

- 工具通道密钥由 `HKDF(code, nonceShare, nonceHelp)` 派生。
- 协助码由 Relay 生成，并保存在 Relay 会话状态和日志中。
- `ToolHello` 与 `ToolHelloAck` 携带双方 nonce，由 Relay 解析外层消息并转发。
- 控制 Relay 进程的攻击者可以获得全部密钥派生输入。

影响：

- 当前 AEAD 能避免普通转发逻辑直接读取工具载荷，也能检测随机篡改。
- 当前 AEAD 不能保证 Relay 失陷后的端到端机密性和真实性。
- 失陷 Relay 可以推导会话密钥，读取或伪造工具请求和响应，最终获得终端文件与命令执行能力。

整改选项：

选项 A：将 Relay 明确定义为可信安全边界。

- 修正文档中“Relay 被攻破也看不见、无法伪造”的描述。
- 使用独立 Relay 主机、严格主机加固、最小权限、补丁、监控和集中审计。
- 接受 Relay 失陷可影响活动会话的剩余风险，并完成正式风险审批。

选项 B：实现真正不信任 Relay 的端到端协议。

- 协助秘密必须由 Share 本地生成，Relay 不得获得完整秘密。
- 将公开会话定位 ID 与秘密认证材料分离。
- 使用经过评审的 PAKE，或带正确身份绑定的 Noise/X25519 协议；不能自行拼装加密协议。
- 会话密钥必须绑定双方身份、协议版本、会话 ID 和完整握手 transcript。
- Relay 只保存定位信息或验证器，不能根据观察到的流量计算会话密钥。

验收标准：

- 安全评审明确选择 A 或 B，并更新威胁模型和产品描述。
- 若选择 B，使用恶意 Relay 测试验证其无法解密、重放、降级或伪造工具消息。
- 使用独立密码学评审和协议测试，不以“单元测试通过”代替安全证明。

### SR-006：ELB 源 IP、SNAT 和 PROXY protocol 行为未确认

- 严重级别：P1
- 状态：OPEN
- 类型：限流失效、全量误封、协议不可用、审计失真
- 代码位置：`internal/relay/server.go:185-198`

证据：

- Relay 直接使用 `conn.RemoteAddr()` 作为每 IP 限流和审计来源。
- Relay 没有 PROXY protocol v1/v2 解析能力。
- 若 ELB 对后端 SNAT，所有公网客户端可能显示为同一个或少量 ELB 地址。
- 若 ELB 向后端注入 PROXY 头，Relay 会把它当成 JSON 协议数据并断开。

影响：

- 单 IP 128 并发限制可能被所有用户共享。
- 在 Relay 后端部署 fail2ban 可能封禁 ELB，造成全量中断。
- 审计日志无法定位真实来源，应用层爆破限制也无法正确工作。

整改要求：

- 在华为云控制台和真实联调中确认 TCP、UDP 后端源 IP 行为。
- PROXY protocol 必须保持关闭，除非 Relay 增加并严格测试可信代理解析。
- 如果后端只能看到 ELB 地址，应在 ELB 或云防火墙完成公网源 IP 限流，Relay 只做全局限流。
- 后端安全组只允许 ELB 来源，禁止绕过 ELB 直连明文端口。

验收标准：

- 使用两个不同公网出口连接，记录 ELB 和 Relay 实际看到的源地址。
- 验证单用户高频请求不会误伤其他用户。
- 验证后端私网 IP 无法从公网直接访问。

### SR-007：候选主机与高权限业务服务混部，扩大失陷影响

- 严重级别：P1
- 状态：OPEN
- 类型：横向移动、业务数据泄露、可用性相互影响

环境证据：

- 候选主机同时运行 DMS、CSB、AppStore、EMQX 等服务。
- 多个 Java 和 EMQX 进程以 root 运行。
- 主机总内存约 7.3 GiB，可用约 1.3 GiB，无 swap。

影响：

- Relay 解析公网输入，一旦出现进程级漏洞，攻击者可能探测本机服务、读取权限配置不当的文件或横向移动。
- UDP/TCP DoS 可能挤占现有业务的内存、文件描述符、CPU、日志和网络带宽。
- 同机 root 业务被利用后，也可以读取 Relay 会话状态和日志。

整改要求：

- 正式环境优先使用独立、无业务数据的 Relay 云主机。
- 使用 `remote-assist` 低权限账号，禁止 root 常驻。
- 保留 `NoNewPrivileges`、`ProtectSystem=strict`、`ProtectHome=true`、`PrivateTmp=true`，并补充 systemd 能力边界、设备、内核、进程和资源限制。
- 配置 `MemoryMax`、`TasksMax`、CPU 和文件描述符上限，避免影响同机服务。
- 限制 Relay 非必要出站网络，避免被利用为横向移动入口。

验收标准：

- 正式部署拓扑确认使用独立主机，或混部风险已经过正式审批。
- 以 Relay 服务账号验证不能读取业务凭据、配置和日志。
- Relay 资源压测不会导致其他业务延迟、OOM 或重启。

### SR-008：ELB 到 Relay 使用明文 TCP，私网链路成为信任边界

- 严重级别：P2
- 状态：OPEN，需要风险决策
- 类型：私网窃听、篡改、错误安全组导致绕过

证据：

- 正式部署方案在 ELB 终止 TLS，Relay 使用 `--plain` 接收后端 TCP。
- 候选主机系统防火墙当前未启用，实际隔离依赖云安全组。

影响：

- 能访问后端网络路径或绕过安全组的攻击者可以观察和修改 Relay 控制协议。
- 即使工具载荷使用 AEAD，注册、Join、协助码和握手元数据仍属于敏感信息。

整改选项：

- 优先评估 ELB 到后端的 TLS 重加密能力。
- 或改用四层 TCP 透传，让 TLS 在 Relay 终止，但需要把正式证书安全地部署到 Relay。
- 若继续使用明文后端，必须限制安全组、子网路由和主机防火墙，并明确接受私网信任边界。

验收标准：

- 从非 ELB 的同 VPC 主机无法连接 Relay 8443/3478。
- 安全组变更有审批、审计和持续配置检查。
- 部署文档明确说明 TLS 终止点和后端明文风险。

### SR-009：协助码是唯一操作授权，未绑定 DMS 操作员和目标设备

- 严重级别：P2
- 状态：OPEN
- 类型：凭据转发、内部滥用、不可追责

证据：

- Relay Join 只验证协助码，不验证 DMS 操作员身份、工单、目标设备或授权范围。
- 持有协助码者可以连接，协助码可以被转发。
- 管家本地确认只控制 Share 是否启动，不能证明实际加入者就是批准的操作员。

整改要求：

- DMS 签发短期、一次性、带签名的授权票据。
- 票据至少绑定操作员、目标设备、会话 ID、签发时间、过期时间和随机 nonce。
- Relay 和 Share 都必须验证票据，防止只绕过其中一端。
- 本地确认界面应展示可验证的操作员和工单信息。
- 协助码继续作为人工核对因子，但不再是唯一身份凭据。

验收标准：

- 有效协助码配错误操作员票据不能建立会话。
- 票据不能跨设备、跨会话使用，重放失败。
- 审计可关联 DMS 操作员、目标设备、本地授权和实际 Help 会话。

### SR-010：公网服务缺少完整的容量保护与安全监控闭环

- 严重级别：P2
- 状态：OPEN
- 类型：资源耗尽、攻击不可见、恢复时间过长

现状：

- 已有 TCP 并发、消息大小和读写超时。
- 缺少会话创建速率、Join 失败速率、UDP PPS、goroutine、内存和带宽上限。
- 尚未形成 ELB、Relay、日志、证书、资源和攻击指标的统一告警。

整改要求：

- 监控 ELB 新建连接、活跃连接、TLS 失败、后端健康、UDP PPS、流量和丢包。
- 监控 Relay 活跃连接、活跃会话、注册速率、Join 失败率、goroutine、RSS、GC、文件描述符和日志速率。
- 配置磁盘、带宽、内存和服务重启告警。
- 建立攻击流量处置、限速调整、回滚和紧急关闭 UDP 的操作手册。
- 使用预期并发和 P2P 失败后的全 Relay 流量执行容量压测。

验收标准：

- 每项关键指标都有阈值、通知人和处置步骤。
- 模拟 TCP 扫描、错误码爆破、UDP Flood 和带宽占满时能触发告警。
- 服务故障、回滚和关闭 UDP 均完成演练。

## 7. 推荐整改顺序

### 阶段 0：缩小首次暴露面

1. 首期仅开放 ELB TLS 8443。
2. Relay 使用 `--stun ""`，不开放 UDP 3478。
3. 客户端固定 `jk-sg.iflyedusvc.com:8443` 并使用 `--insecure=false`。
4. 后端安全组只允许 ELB，禁止公网和其他 VPC 主机直连。

### 阶段 1：关闭 P0 可用性风险

1. 修复 TCP 连接状态机和重复注册。
2. 增加会话数量与创建速率上限。
3. 重构 UDP worker、状态和流量限制，但保持公网 UDP 关闭。
4. 完成 TCP/UDP 攻击压测。

### 阶段 2：关闭凭据与授权风险

1. 删除所有完整协助码日志。
2. 增加 Join 多维限流。
3. 引入 DMS 签名授权票据并绑定操作员与设备。
4. 完成 ELB 源 IP、SNAT 和 PROXY protocol 验证。

### 阶段 3：完成信任边界整改

1. 决定 Relay 是否为可信安全边界。
2. 若不信任 Relay，完成端到端密钥协商重构和独立密码学评审。
3. 使用独立 Relay 主机并完成 systemd、网络和资源隔离。
4. UDP 完成安全验收后再决定是否开放 3478。

## 8. 安全验证矩阵

| 场景 | 预期结果 |
|---|---|
| 单连接重复 register | 第二次被拒绝并断开，会话数不增加 |
| register 后发送 join | 协议状态错误并断开 |
| 高频错误协助码 | 触发限速，合法用户不受全局误伤 |
| 大量空 ClientID 注册 | 会话数和内存始终有界 |
| 超过 4 MiB TCP 消息 | 连接被关闭，进程稳定 |
| TCP slowloris | 读写超时生效，文件描述符可恢复 |
| 随机 UDP session ID | 不创建中继状态 |
| UDP Flood | goroutine、内存、日志和带宽保持有界 |
| 两个公网出口经 ELB 连接 | 源 IP 行为符合设计，限流不互相误伤 |
| 直接访问私网后端 | 非 ELB 来源被安全组和主机防火墙拒绝 |
| TLS 1.2 客户端 | ELB 8443 拒绝 |
| TLS 1.3 + 正确域名 | 证书验证成功 |
| 错误域名或不受信 CA | 客户端拒绝且不生成可用会话 |
| 搜索 Relay 全部日志 | 不存在完整协助码或会话秘密 |
| 错误 DMS 票据 + 正确协助码 | Join 失败 |
| 票据重放或跨设备使用 | Join 失败并产生审计告警 |
| 恶意 Relay 测试 | 结果符合已批准的 Relay 信任模型 |
| 服务重启与主机重启 | 服务恢复，旧秘密不被意外复用 |

## 9. 上线门槛

正式公网开放前必须满足：

- 所有 P0 已修复并通过攻击压测。
- 所有 P1 已修复，或由安全负责人完成书面风险接受。
- Relay 信任模型已经明确，文档描述与实现一致。
- ELB TLS 8443、TLS 1.3、源 IP 行为、后端健康检查和安全组均已实测。
- 客户端使用固定受信域名和 `--insecure=false`。
- 完整协助码不出现在任何日志、监控、错误输出或常规管理界面中。
- 正式制品具有提交号、版本、SHA-256 和可复现构建记录。
- 使用独立 Relay 主机，或混部风险已获得书面批准。
- 安全监控、容量告警、回滚、应急限速和关闭 UDP 流程已经演练。
- UDP 3478 只有在 SR-002 完成整改后才能开放。

## 10. 整改完成后的审核材料

后续审核至少需要提供：

- 每个风险编号对应的代码提交和设计说明。
- 新增或修改的单元测试、集成测试和压测报告。
- ELB、安全组、TLS 策略和源 IP 验证记录。
- 日志脱敏验证结果。
- 制品版本、源码提交、SHA-256 和构建流水线记录。
- systemd 服务文件及 `systemd-analyze security` 结果。
- 独立主机或混部风险决策记录。
- 未关闭风险的负责人、截止时间和书面接受记录。
