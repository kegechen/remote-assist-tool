# 多 relay 节点列表与自动选节点设计（一期）

状态：草案（已按 11-23 反馈修订：域名、证书有效期、日志、黑名单核实与 ping 结论），待最终确认 · 2026-11-23

## 1. 背景与目标

### 1.1 需求

1. 部署多台 relay，客户端自动选用节点；有的机器连不上海外默认节点，要能自动落到其他节点。
2. 协助码全局唯一。
3. 有一个页面新增、停用 relay（放 Cloudflare）。
4. 安全：任何地方都不能出现"谁都能看到所有协助码"的情况。
5. 兼容旧版客户端。

### 1.2 读代码确认的现状（以 master 810842c 为准）

1. **relay 地址只有一个来源链**：编译期默认值 `defaultRelayServerAddr`（`cmd/remote/main.go:541`）→ 环境变量 `REMOTE_RELAY_SERVER` → `--server`。`--server` 的 flag 默认值就是 `defaultRelayServer()`（`cmd/remote/main.go:119/383`），所以"用户是否显式指定"要靠 `fs.Visit` 加检查环境变量来判断，不能看取值。
2. **share 全程只连一个地址**：`reconnectWithBackoff`（`internal/client/share.go:344`）每轮都用 `config.ServerAddr`，`register`（`share.go:392`）带 `RequestCode` 和 `ReuseToken` 申请复用原码。
3. **share 的协助信息里本来就带 relay 地址**：`formatShareInstructions`（`internal/client/share_instructions.go:12`）输出"中转服务: host:port"。MCP `connect` 工具的 `server` 参数说明要求"share 端给了地址就传"（`internal/mcp/schema.go:21`）。**所以旧版 help 走 MCP 时，会跟着协助信息连到 share 实际所在的节点。** 只有两种情况会落到默认节点：CLI `help --code` 不带 `--server`，以及 webui 服务器栏留空。
4. **help 的所有 MCP connect 都汇总到一处**：`help_bootstrap.go:374`，`a.Server` 为空时用进程默认地址。webui 也是起 `remote help --mcp-stdio` 再调 connect。
5. **发码**：`server.go:810` 调 `codes.Generate()`。复用令牌（`internal/relay/reuse.go`）是用 relay 私有 secret 算的 HMAC，换到别的节点验不过。**结论：share 换节点必然换码。**
6. **证书信任**：TOFU，按地址钉证书指纹（`internal/crypto/tofu.go`），首次连接无条件信任。
7. **relay 是信任边界**：会话密钥由"协助码 + 两端 nonce"派生（`internal/proto/handshake.go:146`），三项输入 relay 都能看到（SR-005，状态 OPEN）。**结论：节点列表决定协助码交给谁，节点列表本身就是信任根。**
8. **升级后的新进程总是显式带 `--server`**（`cmd/remote/upgrade_args.go:77`）。自动模式下照搬会把新进程钉死在当前节点。
9. relay 解析消息时不拒绝未知字段（只有 limits 文件和 update-info 文件用了 `DisallowUnknownFields`）。所以新字段可以直接加在 Register/Join 的请求和响应里，旧 relay 会忽略。
10. **黑名单计分（在 `feat/relay-reconnect-grace` 上核实，线上两台跑的就是这个系列；master 没有黑名单）**：
    - TLS 握手阶段对端中止（EOF、重置、超时、alert、握手到一半被取消）归 `KindTLSAborted`，**权重 0，只记事件**（`blocklist/list.go` 的 `kindWeight`，`server.go` 的 `classifyHandshakeErr`）。
    - 握手完成后不发任何消息就断开：读循环里 `scanner.Scan()` 返回 false 直接 return，**不计分**。
    - 所以"并行建连、输的那路断开"（也就是 dial.go 里 TCP/QUIC 竞速已经在做的事）不会被记分。
    - **危险点在另一处**：连接未注册时收到未知消息类型，`KindUnknownMessage` 计 1 分，`before_register` 计 2 分，封禁阈值 20 分；只有该 IP 近期有过成功注册/加入才豁免。一个新增的 ping 消息发给没升级的 relay 会被计分，共用出口 IP 的一批用户可能被一起封。
    - 副作用：每条这样的连接都会被记成一次扫描（outcome=`scanned`），连接统计会有偏差。
11. **目录域名**：Worker 放在本仓库之外的独立 Workers 项目里，一个子目录一个 Worker，各占一个 `<名>.ifly.qzz.io` 子域（`workers_dev = false`，`custom_domain = true`），密钥用 `wrangler secret`，KV 绑定写在各自的 `wrangler.toml`。

### 1.3 目标

- 客户端从 Cloudflare 拿到签名的节点列表，按策略自动选节点。拿不到就用 relay 转发的副本或本地缓存，都不可用时用内置默认节点。
- 协助码首位表示节点，**唯一性由构造保证**，不需要任何中心存储。
- 日常的启用、排空、停用、调权重在 CF 页面上完成。新增、吊销节点需要本机根密钥签名。
- CF 账号被盗、镜像被篡改、遇到中间人时，都无法让客户端连上未经根密钥认可的 relay。
- 未配置节点模式的 relay 行为和现在完全一样；显式指定了 `--server` 的客户端只连指定的地址、照旧 TOFU，只多学 relay 转发的列表（6.1）。

### 1.4 非目标（一期不做）

- relay 间转发和桥接。
- SR-005 端到端改造（PAKE，让 relay 看不到完整码），另行立项。
- share 同时挂在多个节点上。
- 节点信息的可视化展示。

## 2. 总体结构

```
你本机（离线）                    Cloudflare                     relay 节点                   客户端
┌──────────────┐  节点证书    ┌───────────────────┐  签名列表  ┌──────────────┐  签名列表  ┌──────────────┐
│ relay-admin  │ ───────────▶ │ Worker + KV       │ ────────▶ │ 定时拉取、缓存 │ ────────▶ │ 验签 → 缓存   │
│ 根私钥（主/备）│  状态密钥授权  │ 管理页（Access 保护）│ GET 公开   │ 按自身状态执行 │ 注册/加入   │ share 选节点  │
└──────────────┘              │ 状态私钥签整份列表    │ ─────────────────────────────────▶ │ help 按前缀路由│
                              └───────────────────┘                                    └──────────────┘
```

**CF 上不存任何协助码，哈希也不存。** 协助码明文只存在于签发它的那台 relay 的内存里（和现在一样，审计日志只记指纹）。

## 3. 信任与密钥

### 3.1 三层签名

| 层 | 密钥位置 | 签什么 | 什么时候用 |
|---|---|---|---|
| 根密钥（主、备两把） | 你本机，用口令加密；备用那把移到离线介质 | 节点证书、状态密钥授权、吊销列表 | 新增节点、续期、吊销、更换状态密钥 |
| 状态密钥 | CF Worker secret | 整份节点列表（状态、权重、策略、序号、有效期） | 管理页每次保存、每日定时重签 |
| 根公钥（主、备） | 编进客户端和 relay（`internal/directory/roots.go`） | — | 验签 |

客户端只有在下面四条全部满足时才使用一个节点：
1. 列表由状态密钥签名；
2. 状态密钥由某把未被吊销的根密钥授权，且在有效期内；
3. 该节点的证书由某把未被吊销的根密钥签发，且在有效期内；
4. 证书序号不在吊销列表里。

### 3.2 本机文件（生成后再向你确认最终路径）

```
%USERPROFILE%\.remote-assist-admin\
  root-primary.key / .pub   主根密钥（scrypt + XChaCha20-Poly1305 加密，口令由你自己输入）
  root-backup.key  / .pub   备用根密钥：整个目录备份到 U 盘或密码管理器后，从本机删掉 .key（.pub 是公开信息，留在本机，工具靠它认出备用根签的东西）
  ledger.json               已签发的节点证书台账（前缀、序号），用来防止前缀重复
  issued\                   签出的节点证书、状态密钥授权、吊销列表
```

- 状态私钥只在本机生成一次，用 `wrangler secret put` 上传到 CF 后就从本机删除。丢了也没关系，重新生成一把再授权即可。
- 根私钥丢失的后果：没法再新增节点，也没法更换状态密钥，只能发一个内置新公钥的客户端版本。**所以备份很关键**，备用根密钥就是为这个准备的。
- 实现只用 `golang.org/x/crypto`（已在 go.mod 里）和标准库 `crypto/ed25519`，不引入新依赖。

### 3.3 各种威胁的后果

| 事件 | 后果 | 处置 |
|---|---|---|
| CF 账号被盗，或状态密钥泄露 | 可以停用节点、乱调权重（影响可用性）；**加不进新节点** | 用根密钥授权一把新的状态密钥，序号更高的授权会让旧的作废。攻击者把列表序号推到极大值也卡不住客户端：新授权的列表序号从头算（见下面“回放旧列表”） |
| 列表在传输中或镜像处被篡改 | 验签失败，客户端丢弃这份列表 | — |
| 回放旧列表 | 客户端记住已接受的最新位置（授权根、状态密钥授权序号、列表序号），按「授权序号优先、同一授权内比列表序号」比较，只接受不低于它的列表；本地缓存被删时，回放窗口受列表有效期（30 天）限制 | — |
| 某个节点被入侵 | 可以拿到落在它上面的会话（SR-005） | 用根密钥吊销该节点证书。CF 上的"停用"可以被再次启用，挡不住被入侵的节点 |
| 主根密钥泄露 | 攻击者可以签发恶意节点，也能用主根签的吊销列表乱吊销节点、把状态密钥序号下限推到极大值（让所有列表都被拒） | 用备用根密钥签发吊销（吊销主根），同时声明状态密钥序号下限，再用备用根授权新的状态密钥，两者一起上传。客户端会持久记住这条吊销；此前由主根授权的位置随之作废，主根签过的节点吊销和序号下限一并失效，此前授权的旧状态密钥（哪怕由备用根授权）也因序号下限而作废。根吊销是单向的：**只有备用根能签、且只能吊销主根**，所以攻击者拿到主根也吊销不了备用根 |
| 备用根密钥泄露 | 同上，且能用它吊销主根 | 只能发版：先用主根授权一把新状态密钥，再在 `roots.go` 里内置吊销那把备用根公钥的指纹、换上新的备用根公钥，并把内置状态密钥序号下限抬到新状态密钥的序号（见下面“发版写内置吊销根”）。发版后它签过的根吊销失效，主根恢复可用。新备用根的生成：`relay-admin` 目前没有换根的命令，在一个临时目录运行 `relay-admin --dir <临时目录> keygen`，只把其中的 `root-backup.key/.pub` 拷进管理目录替换旧的（旧的另行存档），临时目录里的主根和台账丢弃；管理目录的主根和台账不动。`roots.go` 里**只换 backup 那一行**，primary 保持原值——临时目录 keygen 打印的 primary 公钥是要丢弃的临时主根，编进去的话新版本客户端会拒收真正主根签的一切。新的 `root-backup.key` 按 3.2 备份到离线介质、确认无误后从本机删掉（`.pub` 留下）。建议先运行下面 ① 说的 `revoke --root backup` 看清单、按清单用主根重签，再换文件；换了之后再运行，旧备用根签的证书也会照样列出（注明由已换掉的旧根签发）。过渡期内旧版本客户端不认新备用根，状态密钥授权、吊销列表、节点证书都只用主根签（同下面“例行轮换”）。另外两件事：① 它签过的**全部**吊销（含节点吊销）对新版本客户端一并失效：节点列表里内嵌的吊销若由旧备用根签，新版本客户端验签不过、**整份拒收节点列表**，只能退回内置默认节点。所以发版前必须用主根把累积的吊销重签一份、上传替换（`relay-admin revoke --resign`；`revoke --root backup` 被拒时会列出这一步和要改由主根重签的节点证书）；② 主根此前若已被吊销，先分清是不是攻击者拿泄露的备用根干的——是的话主根没事，照上面处理，发版后自然恢复；若是因为主根自己也泄露过而正当吊销的，发版时主根的指纹也要写进内置吊销、同时换上新的主根公钥，此时两把根都换新，新状态密钥授权、吊销列表、节点证书都改由新根签（`relay-admin` 目前没有换根的命令，到时再加） |
| 第三方节点推钓鱼下载链接 | 客户端会忽略它下发的链接（见 6.6） | — |

**吊销的记法**（上表各条处置都依赖它）：

- 根吊销记的是**根公钥的指纹**（公钥字节的 sha256 小写 hex），不是 `primary`/`backup` 这个名字。名字只决定角色（谁能签根吊销）；发版换上新公钥后，即使仍叫 `primary`，旧公钥的吊销也不波及它。
- 客户端**按签发者分别记**吊销：每把根一条记录，内容是它签过的节点吊销、根吊销、状态密钥序号下限的并集（只增不减）。合成规则：
  1. 内置吊销（`roots.go`）无条件生效；
  2. 记录里的根吊销：签发它的根没被内置吊销就生效（所以备用根泄露只能靠发版作废它签的根吊销）；
  3. 记录里的节点吊销和序号下限：签发它的根没被吊销（内置或第 2 步）才生效（所以主根被吊销后，它灌进来的东西随之作废）。
- 每把根的记录合并后节点证书序号最多 1024 个、根最多 4 把，超出整份列表拒收，客户端缓存的大小有上限。
- 已知且接受的代价：主根在被吊销前可以用「只含节点吊销 + 极大序号下限」的吊销列表让客户端拒收全部列表。恢复路径就是上表的处置——备用根吊销主根之后，主根签的下限不再生效。
- **发版写内置吊销根时，必须同时抬高内置状态密钥序号下限**（`Roots.MinStatusSerial`）：主根被吊销的情形至少抬到那份吊销列表声明的下限（`relay-admin revoke --root` 会打印这个数），备用根泄露的情形抬到发版前新授权的状态密钥的序号。原因：根被吊销后，客户端在它名下记住的位置作废，序号下限退回「内置值与吊销列表声明值」中的较大者；新装、从没收到那份吊销列表的客户端只有内置值，内置值不抬，此前已被取代的旧状态密钥（由另一把根授权）就能重新生效。`roots.go` 有测试检查「有内置吊销根时下限不为 0」，挡住忘了抬的情形；抬到多少要按上面取值。同时要把被吊销的那把公钥从 `Keys` 里删掉或换上新公钥（同一个测试会查，`relay-admin revoke --root` 也会提示）：客户端判断根吊销只看签发者是不是备用根、吊销的是不是它自己，不需要 `Keys` 里还留着被吊销的公钥。
- **例行轮换一把根（没有泄露）也要经另一把根过渡**：新旧版本客户端内置的根不同（例如旧版是 P/B，新版是 P2/B），任何由 P 或 P2 签的东西都只有一边认。过渡期内状态密钥授权、吊销列表和节点证书都改用两边都认识的那把根（这里是 B）签，等旧版本基本退出后再启用新根。不这样做，「P 授权状态密钥 + P2 签吊销列表」之类的组合新旧客户端都会整份拒收。目前 `relay-admin` 没有单独轮换一把根的命令，需要时再加。

## 4. 节点列表格式

所有签名对象都用同一种信封格式。签名作用在原始 payload 字节上，不需要做 JSON 规范化：

```json
{ "kind": "node-cert|status-key|revocations|directory", "payload": "<base64(JSON 字节)>", "sig": "<base64(Ed25519 签名)>", "signer": "primary|backup|status" }
```

- 实际被签名的字节串是 `"remote-assist-directory-v1" 0x00 kind 0x00 payload`。`kind` 参与签名（域分离），所以一种对象的签名不能被重放成另一种对象（例如把节点证书冒充成状态密钥授权）。
- 节点入网申请用另一个独立的签名域（`remote-assist-node-request-v1`），由 relay 的 TLS 证书私钥签名，与上面的根签名互不相通。换证书申请还要由旧证书私钥在第三个域（`remote-assist-node-request-prev-v1`）共签，两个签名不能互换。

**节点证书**（根密钥签发）：

```json
{
  "serial": 7,
  "prefix": "K",
  "name": "海外 1",
  "operator": "<运营者>",
  "official": true,
  "region": "overseas",
  "tcp":  ["<host>:8443"],
  "quic": ["<host>:8443"],
  "tls_fps": ["<relay 证书 DER 的 sha256 hex，同 crypto.CertFingerprint>"],
  "not_before": 1795000000,
  "not_after": 1826536000
}
```

- `tls_fps` 有 1–2 个（小写 hex、互不重复）：平时一个；换证书期间是「新、旧」两个，节点切换 TLS 证书时客户端不断连（流程见第 9 节“换证书”）。
- 地址每类最多 4 个，`host:port` 只允许可打印 ASCII，端口 1–65535 且不带前导零；名字、运营者等文本字段最长 64 字节，只允许字母、数字、标点、符号（Unicode L/N/P/S 类），并排除其中显示为空白的填充字符（如 U+3164、U+2800、U+13441、U+1D159）和「数学字母数字符号」区块（U+1D400–U+1D7FF，粗体、等宽等样式的拉丁字母和数字，显示出来就是普通 ASCII）；控制字符、零宽与双向控制、空白、组合附加符、私用区一律拒绝（防终端注入，也防用看不见的字符把两个节点名伪装成一样）。
- `official=false` 表示第三方节点：客户端不展示它下发的升级链接，并在协助信息里标明运营者。
- 有效期统一 1 年（`relay-admin sign-node --valid` 默认 365 天，对不太熟的第三方可在签发时缩短）。到期前 30 天管理页提醒续签。

**状态密钥授权**（根密钥签发）：`{ "serial": 1, "pubkey": "<base64>", "not_before": ..., "not_after": ... }`

**吊销列表**（根密钥签发）：`{ "serial": 3, "issued_at": ..., "node_serials": [5], "roots": ["<根公钥指纹>"], "min_status_serial": 1795000000 }`。

- 每份都包含以往全部吊销条目（累积）。根吊销只能由备用根签、只能吊销主根、不能吊销自己；`roots` 里写根公钥指纹（见 3.3「吊销的记法」）。
- `min_status_serial`（可省略）是状态密钥授权序号的下限，低于它的授权一律作废。吊销主根时必须声明（`relay-admin revoke --root primary` 自动取当前时间），否则主根留下的位置作废后，早已被取代的旧状态密钥会重新生效。
- 吊销只增不减：客户端对见过的吊销取并集，吊销列表的序号只给台账排序用、不参与验证——旧吊销列表撤销不了已记住的吊销，而拒收低序号吊销反会让攻击者用一个极大序号挡住之后的合法吊销。
- 单份最多 1024 个节点证书序号、4 把根。

**信封解析是严格的**：未知字段、信封之后的多余内容都拒收。信封里只有 `kind`、`payload` 参与签名，放过不参与签名的内容，转发者（镜像、中间人）就能往客户端缓存里塞东西。JSON 重复键按最后一个取值，挡不住，所以缓存只存重新编码后的信封（见 6.2）。

**节点列表**：对外发布的是一个信封（`kind` 为 `directory`，`signer` 为 `status`，由状态密钥签名），payload 是下面的正文：

```json
{
  "format": 1,
  "serial": 42,
  "issued_at": 1795000000,
  "expires_at": 1797592000,
  "policy": "prefer-default",
  "default_prefix": "K",
  "status_key": { "kind": "status-key", "payload": "...", "sig": "...", "signer": "primary" },
  "revocations": { "kind": "revocations", "payload": "...", "sig": "...", "signer": "primary" },
  "nodes": [
    { "cert": { "kind": "node-cert", "payload": "...", "sig": "...", "signer": "primary" }, "status": "active", "weight": 100 }
  ]
}
```

- `policy`：`prefer-default`（过渡期默认值：默认节点优先）或 `fastest`（纯最快）。
- `status`：`active`（启用）、`draining`（排空）、`disabled`（停用）。
- `weight`：0–100，0 表示不参与自动选择。
- 客户端会拒绝以下列表：前缀、证书序号或证书指纹重复，`default_prefix` 对不上节点，超出有效期（允许 ±1 天时钟误差），位置回退（见 3.3），自身有效期超过 45 天，节点数超过 32，整份超过 256 KB。
- 单个节点的问题（证书过期、被吊销、签名不对、`weight` 越界，以及这一项的字段类型不对、根本不是对象等）只丢弃这个节点并记下原因，不连累整份列表。`default_prefix` 指向的节点被丢弃时列表仍然有效，客户端按其余节点选择；有被丢弃的项连前缀都读不出来（不是对象之类）时，它可能就是默认节点，`default_prefix` 对不上也不拒收（这项核对只为发现写错的配置，挡不住状态密钥持有者）。

## 5. 协助码

- 码长仍为 12 位，字符集不变。**首位等于节点前缀**，后 11 位随机，约 54.5 bit。旧客户端不校验码格式（help 只去掉分隔符，见 `help.go:431`），所以格式上完全兼容。
- relay 不用配置自己的前缀：它拉到列表后，用**自己的 TLS 证书指纹**在列表里找到自己，前缀和状态都从证书里取。找不到自己时不进入节点模式，照旧发全随机码，并打警告日志。
- share 申请复用一个前缀不是本节点的旧码时，复用令牌本来就验不过（见 1.2 第 5 条），会自然换成新码。
- **过渡期旧码**：relay 升级前发的码首位是随机的，其中一部分会碰巧等于别的节点的前缀。这类码最多存活 `--code-max-age`（默认 24h）。help 的回退规则见 6.4。

## 6. 客户端行为

### 6.1 显式模式和自动模式

| 入口 | 什么算显式 |
|---|---|
| share / help CLI | 用户写了 `--server`（通过 `fs.Visit` 判断，写的正是内置地址也算），或设置了 `REMOTE_RELAY_SERVER`（只有空白不算），或用了 `--standalone`（只有 share 有）、`--plain`（只用于开发：节点都要 TLS 并按列表里的证书校验，明文连不了） |
| MCP connect | 调用时带了 `server` 参数；没带时，看 MCP 进程本身是否显式（进程按上一行判定） |
| webui | 服务器栏填了地址（作为 connect 的 `server` 参数传下去，help 子进程也带 `--server`）。留空时，GUI 进程设了 `REMOTE_RELAY_SERVER` 就让子进程带 `--server` 用它（子进程显式，connect 不带 `server`），否则子进程和 connect 都不带地址 |

- **显式模式和现在一样**（只连指定的地址、TOFU、不测速），只多学列表：注册、加入时同样带上本地缓存的列表位置（6.2 第 2 条），收下 relay 随响应转发的列表；连上的 relay 证书指纹在列表里某个节点的 `tls_fps` 里、连的又不是它在列表里的地址时，把这个地址记为该节点的"本机专用地址"（见 6.5）。显式进程不取 CF，也不读 `REMOTE_RELAY_DIRECTORY`：只能用 `--server` 连上国内节点的机器靠 relay 转发拿到列表。`--standalone`、`--plain` 连的不是列表节点，什么都不学。显式进程里缓存有问题（损坏、读不了）的提示不带「按内置默认节点连接」，那不适用。
- 显式 share 被排空的节点以 `NODE_DRAINING` 拒绝时（排空的 relay 拒绝声明了列表能力的新注册，第 7 节），本进程之后注册不再带列表位置，像旧客户端一样被接纳，并提示一行。代价是多一次被拒，换来显式 share 照样能靠 relay 拿到列表。
- 自动模式的 MCP 进程里带 `server` 的 connect：照旧连这个地址，证书按这个地址属于哪个节点来校验，不是认列表里任一节点——那样列表里任何一个运营者都能冒充别的节点的地址，收下发往那里的协助码。地址是列表里某个节点的地址（TCP、QUIC 地址都算，主机名不分大小写）时只认这个节点的 `tls_fps`，严格比对、不走 TOFU、不写指纹表，也只用这个地址声明过的传输，与 6.3 相同；是某个节点记下的本机专用地址（6.5）时，这个节点的证书直接放行、不查也不写指纹表（节点按列表换了证书时，按地址记的旧指纹会对不上），别的证书照旧 TOFU；两样都不是时照旧 TOFU，连上的若是列表节点就照常记为它的本机专用地址，之后这个节点换证书也连得上。两者冲突（本机专用地址恰好是别的节点的列表地址）时以列表为准。这类 connect 也在后台按 `RefreshIfStale` 的规则刷新列表（同 6.4 第 3 条）：列表地址按列表严格比对，列表旧了就连不上，只能靠 CF 更新。连上的属于列表节点时，展示和升级提示链接按该节点（6.6、6.7）；但连的地址是别的节点的列表地址时不算（还没有能用的列表、照旧 TOFU 连上后，relay 转发来的列表说地址属于 D，出示的却是 E 的证书），警告一次「可能被劫持」，展示、升级链接照旧按不在列表节点上处理，下一次连接有了列表就按 D 严格比对。显式的 MCP 进程（命令行写了 `--server` 等）照旧 TOFU、展示不变，只学列表。
- 其余情况都是自动模式。
- webui 的自动重连沿用当初的判定。通道内升级后连新 share 时，连 old 是自动模式（服务器栏留空、GUI 也没设 `REMOTE_RELAY_SERVER`）就不带新 share 在 code 文件里写的地址，仍按新码找节点：那样会先试这个节点的本机专用地址，写下的是列表里的公开地址，这边不一定连得上。其余情况照旧连写下的地址（新 share 在列表节点上时写的是列表里的地址，不是它的本机专用地址，见 6.3）；连不上（比如这边只能经内网地址连那个节点）就按连 old 时用的地址再试一次，这个地址这边刚连通过，新 share 多半还在同一台 relay 上。两者相同（补上默认端口后比，不分大小写）时不重试；只有连 relay 这一步网络不通（连不上、被拒、超时）才重试：证书、TLS 的错误（指纹变了、与节点列表不符、不受信任）和连上后被断开都不算，前者说明连到了写下的地址、对方的证书不对（可能是中间人），换地址连上会把这个警告盖过去；错误经 MCP 传来时只剩文本，按文本里的网络错误字样判断，带证书、TLS 字样的一律不算（地址是用户写的，可能碰巧带这些字样）。加入、握手阶段超时说明已经连到了写下的地址，被 relay 封禁、协助码不对时换地址也没用，多连一次还让 relay 多记一次失败。重试前的进度提示写明第一次失败的原因和改连的地址；两次都失败时照常回连 old，报错里带上两次的原因。

### 6.2 获取和缓存列表

来源有三个，拿到的都是同一份签名内容，按序号取最新的：

1. **CF**：`GET https://relay-list.ifly.qzz.io/v1/directory`。地址是编译期常量（`internal/directory`），可用环境变量 `REMOTE_RELAY_DIRECTORY` 覆盖，设成空（或只有空白）或 `off` 表示不取 CF（Windows 的 cmd 里 `set REMOTE_RELAY_DIRECTORY=` 是删掉变量，所以要有 `off`）；设了但不是合法的 https 地址（要有主机名、不带用户名密码）时提示一次并同样不取 CF，不悄悄改用内置地址，提示里不写地址的内容（可能带着令牌）。它和默认 relay 地址一样是公开服务地址，不含个人信息。必须用自定义域名，`workers.dev` 在国内基本不通。超时 3 秒，和连接并行，不拖慢连接。share 启动时取一次，之后每 6 小时取一次（没有列表时被默认节点以排空、停用拒绝，也马上取一次，见 6.3）。help 在缓存超过 6 小时时于后台刷新：缓存的年龄取本进程上次从 CF 确认过的时间（收下了，或 CF 那份不比缓存新）与列表签发时间中较晚的那个（都按墙上时间算，睡眠的时间也算进去）；本机没有能用的列表（没有、过期了、缓存读不了）时谈不上年龄，照样要取。不管哪种情况，本进程上次向 CF 发请求后 1 分钟内不再发（MCP 每次连接都会问一次，CF 不通时不能每次都多等 3 秒）。同一进程里同时要取的（后台刷新加上找不到前缀时的同步取）合并成一个请求。
2. **relay 转发**：注册或加入时带上本地缓存的序号，relay 手里的更新就在响应里一并下发。
3. **本地缓存**：`~/.remote_assist_relays.json`，保存信封、已接受的最新位置、按签发根分别记的吊销（见 3.3）、本机专用地址。**每次读取都重新验签**，不盲信缓存。
   - 存的是重新编码后的信封，不是收到的原文：原文里不参与签名的部分（重复键、空白）不进缓存，免得被撑过 1 MB 上限后整个文件当损坏处理、丢掉已记住的位置和吊销。位置相同但缓存里那份已经验不过（文件被改坏）时，用新收到的修复。位置相同时列表不换，但新收到的那份若带来缓存里还没有的吊销（Worker 违约用同一序号重签了两份），照样记进状态：吊销只增不减，不能只在这一次会话里生效。
   - 多个进程（share、help、MCP）用旁边的 `.lock` 文件协调（Windows `LockFileEx`、unix `flock`）：更新取排他锁，读取取共享锁（Windows 上有进程开着文件时，写入方的 rename 会失败）。`.lock` 文件永不删除。杀毒软件、索引服务不走这把锁，它们短暂打开文件时 Windows 上的 rename 同样失败，写入方遇到拒绝访问、共享冲突、锁冲突时最多重试约 1 秒。
   - 缓存文件损坏时，读取照常退回内置默认节点，但**拒绝更新**、不覆盖文件：从空缓存重来等于忘掉已记住的位置和吊销，旧列表就能回放。错误里带文件路径，提示用户删掉它重置。
   - 版本号高于本程序认识的（更新的版本写的）不算损坏：读取同样退回内置默认节点、拒绝更新，但提示升级，**不提示删除**——删掉会丢掉更新版本记住的位置和吊销。本程序不认识的顶层字段写回时原样保留，所以新版本可以加顶层字段而不升版本号，前提是旧版本原样带着它不出错（例如只在列表里还有这个节点时才使用的本机专用地址）；需要随列表更新而改写的字段，以及 `state` 里的任何新字段（旧版本按自己的理解重建 `state`，会丢掉它们），都必须升版本号。`version` 永远是文件里的第一个字段：更新的版本可以放宽 1 MB 上限，旧版本读不全超大的文件，只能从开头认出版本号，认出更高的就照上面提示升级，认不出才当损坏。

列表过期（超过 `expires_at`）就作废，退回内置默认节点。

### 6.3 share 选节点（自动模式）

- **候选**：`status=active`、`weight>0`、证书有效且未吊销的节点。地址先试本机专用地址，再试列表里的地址；每个地址仍走现有的 TCP/QUIC 竞速（`dial.go:47`）。
- **`prefer-default` 策略**：先按正常流程连默认节点，连上就用。连不上时，对其余候选并行建连，**第一个完成握手的直接拿来用**，其他连接关掉。握手最快就是 RTT 最低，不需要额外测速。
- **`fastest` 策略**：所有候选（包括默认节点）一起并行建连。按权重错开起跑时间，`(100 - weight) × 3ms`，最多晚 300ms，这样权重高的节点在 RTT 接近时胜出。
- **粘性**：注册成功后，断线重连先回当前节点；**连续失败 3 次才重新选节点**。在健康节点上不会主动换节点：换节点就会换码，默认节点恢复后也不迁回。
- **排空迁移**：注册响应里带 `node_status=draining`，或者新拿到的列表把当前节点标成排空时，等没有协助端连接（处于等待协助端阶段）时再重新选节点、重新注册，然后沿用现有的 `codeChangeNotice` 提示，刷新剪贴板和 code-file。有协助端连着时不动。注册时不在列表节点上（第一次运行在默认地址上注册、列表随注册响应才下发；列表失效后回到默认地址，之后又拿到列表）时，按这条连接出示的证书在列表里认出所在节点再判断，不按地址认（理由见下面「换了 relay 不带原码」）；认不出就不迁移，与没有这个功能时一样。
- **证书校验**：relay 出示的证书指纹必须是列表里 `tls_fps` 之一，严格比对，不走 TOFU。不一致就当作这个节点连不上，跳过，并警告"节点 X 证书与列表不符，可能被劫持"。
- **换了 relay 不带原码**：码和复用令牌只在发它的 relay 上有效，带给别的节点等于把令牌交给别的运营者，所以重连注册前先判断现在连的是不是注册这个码的那台 relay，不是就不带 `RequestCode` / `ReuseToken`，并提示换码。判断方法：
  - 注册时和现在都在列表节点上：比前缀。前缀相同就是同一个节点（地址、指纹可以随列表更新而变）；前缀不同就是换了，地址相同也一样（地址可能已换给别的节点）。
  - 都不在列表节点上（显式模式、一直没有列表）：比地址，与没有这个功能时一样。
  - 一边在、一边不在（第一次运行没有列表、列表随注册响应才下发；列表失效后回到默认地址）：比证书指纹，注册那条连接出示的证书在节点的 `tls_fps` 里（或反过来）才算同一台。不按地址认：同一台 relay 可以有几个地址，同一个地址也可能出示别人的证书。
- **没有列表时默认节点在排空**：排空的 relay 拒绝声明了列表能力的新注册（第 7 节），可没有列表的客户端无从改选。被 `NODE_DRAINING` 或 `NODE_DISABLED` 拒绝时，马上按 6.2 的 `RefreshIfStale` 规则同步从 CF 取一次列表，取到了下次就按列表选节点；是排空的话，本进程之后在没有列表时注册不再声明能力，像旧客户端一样被接纳（码在默认节点上，与没有这个功能时一样）。代价是这期间收不到 relay 转发的列表，只能等 CF。
- **升级后的新进程**：旧进程是自动模式（argv 里没有 `--server`）时，`upgradedShareArgs` 不写 `--server`，改传内部旗标 `--relay-hint=<当前节点地址>`。新进程先试这个地址，但仍是自动模式。
- **code-file**：`server` 字段与协助信息里「中转服务」一行写同一个地址（6.7）：显式模式、不在列表节点上时照旧写实际连上的地址；在列表节点上时写列表里的地址。读它的宿主程序和 webui 通道内升级都是把它交给协助端用的，本机专用地址协助端多半连不上。

### 6.4 help 路由（自动模式）

1. 码先按 relay 的规则规范化（去掉 `-`、空格、`_`，再 `strings.ToUpper`，两边必须一致，否则同一个码会落到不同节点，例如 `ſ` 大写后是 `S`），取首位作为前缀。`--no-auth` 的固定码（`proto.NoAuthCode`）不是任何节点发的，不路由，首位碰巧是某个节点的前缀也一样；它也不触发第 3 条的同步取。
2. 列表有效、能找到这个前缀、节点没被停用时，连这个节点（先试本机专用地址，再试列表地址；排空的节点照样连，它仍接受自己发过的码）。证书按列表严格比对（同 6.3）；这台连不上或证书不符就报错，不改连别的节点：码只在发它的节点上有效，换节点只会多一次加入失败。每次加入（含 MCP 的自动重连）都按码重新找，help 不粘节点、不退避。
3. 每次加入都在后台按 6.2 的 `RefreshIfStale` 规则刷新列表，不等它。找不到前缀时：同步等这次取（与后台那次是同一个请求，最多 3 秒，含等缓存文件锁的时间）：本地没有能用的列表（没有、过期了、缓存读不了），或列表超过 6 小时没确认过，就取；刚在后台取过的（1 分钟内）不重复取，正在取的等它的结果。还是找不到就连默认节点：列表里的默认节点（没被停用时），否则内置默认地址（按配置走 TOFU，与没有列表时一样）。
4. **过渡期回退**：按前缀连到节点 X（X 不是默认节点）且 relay 明确拒绝加入时，再去默认节点（同第 3 条的默认节点）试一次，用来接住 5 节中的旧码。这次失败只在 X 上计一次失败分，可以接受。被封禁、连不上 X 都不回退；回退也失败时报 X 上的错误（码的首位说它属于 X）。两个版本之后删掉这条回退。
5. MCP connect 的幂等判断：没带 `server` 的自动连接，连上之前不知道会连哪台，只比码（码决定了节点），且活动会话也得是自动连上的；带了 `server` 的，与活动会话实际连着的地址比（`connectTarget.Server` 记录路由后的实际地址），所以显式指定刚才路由到的那台会复用。自动重连沿用调用方原来的参数（没带 `server` 就仍是自动），重新按码找。
6. P2P 的 STUN（也是 UDP 中继）地址跟着实际连上的节点（relay 主机的 3478），不按默认地址推导；指定了 `--stun` 的照旧。share 自动模式同样。进程是自动模式时，MCP connect 带了 server 的、拿不到节点列表（如拿不到家目录）而连默认地址的，STUN 也跟着实际连上的 relay——这时没有按默认地址推导出的 STUN 可用，UDP 中继也只认在它那里注册过的会话。relay 在私网或本机时 `--p2p auto` 跳过 P2P（relay 已是 LAN 直连）：显式模式在连接前按 `--server` 判断，与现在一样；自动模式连上之后按实际连的地址判断（命令行和 MCP 都是）。

### 6.5 本机专用地址（即"用 `--server` 引导一次"）

- **记录**：显式连上地址 A（含自动模式 MCP 进程里带 `server` 的 connect），A 处 relay 的证书指纹在列表中节点 N 的 `tls_fps` 里（不论 N 的状态），A 又不是列表里的地址（N 或别的节点的 TCP、QUIC 地址都算，不分大小写；是别的节点的地址时以列表为准，不记，也不当作连上了 N，警告一次「可能被劫持」，见 6.1），就把 A 记为 N 的本机专用地址；记的已经是 A 时不重复记、不重复提示。典型用途：内网地址、Tailscale 地址，或者首次只能手动指定的国内节点。
- **使用**：自动模式连 N 时先试 A。自动模式 MCP 进程里带 `server` 连 A 时，N 的证书免 TOFU（6.1）。
- **清理**（按你定的规则）：A 连不上一次就删掉，回到策略顺序（默认节点优先）。删掉的只是这个地址，列表还在，所以客户端仍然知道 N 的公开地址。**按地址删**：只在缓存里当前记的就是刚才连不上的这个 A 时才删。多个进程共用缓存文件，长时间运行的 share 手里是旧地址，期间别的进程可能已把 N 改记为新地址，按节点删会把刚记下的、能用的地址一起删掉。
- **清理必须让用户知道**：删除时同时输出到终端和日志文件（见 6.8），固定格式，share 控制台和 help 的 stderr 都打（MCP 模式只走 stderr，不污染 stdout 协议通道）：
  ```
  [relay] 本机专用地址 <A> 连接失败（<原因，如 timeout / refused / 证书指纹不符>），已从缓存删除，改用节点列表（默认节点优先）。如需固定使用，请设置 REMOTE_RELAY_SERVER。
  ```
  - 以下情况也各打一行：记录新的本机专用地址（`已记住 <A> 为节点 <名称>（<前缀>）的本机专用地址`）、首次拿到列表（`已获取节点列表（来自 <CF 主机名或 relay 地址>）: 序号 42，启用 N 个节点`）、列表更新（`节点列表已更新（来自 <CF 主机名或 relay 地址>）: 序号 41 → 42，启用 N 个节点`；换了状态密钥时写成 `状态密钥授权 1 → 2，序号 41 → 1`，免得看成序号倒退）、列表验签失败被丢弃（含失败的是哪一层）、列表里个别节点被丢弃（`节点列表里的节点 "<前缀>"（证书序号 N）已丢弃: <原因>`）、缓存过期、选节点结果。同一个问题（CF 取不到、缓存损坏、列表过期等）只在出现时打一次，消失后再出现才再打：share 每 6 小时、MCP 每次连接都可能遇到同一个问题。被丢弃的节点按（前缀、证书序号、原因类别）去重，长期留在列表里的坏节点不会因为 Worker 每重签一次列表就重复提示；原因变了、节点从列表里消失后又出现、或同一键下多出一项，才再提示。
  - 日志里只写节点前缀、名称、地址，不写协助码（见 6.8 的脱敏）。
- **不在列表里的 relay 不记录**：自动模式永远不会连上没有根签名的 relay。自建 relay 想长期固定使用，请用 `REMOTE_RELAY_SERVER`。

### 6.6 升级提示链接

自动模式下（含自动模式 MCP 进程里带 `server`、连上的是列表节点的 connect，见 6.1），如果节点证书是 `official=false`，客户端忽略这个 relay 下发的 `download_url` 和 `release_page`，改用编译期默认值（`update.DefaultDownloadURL` / `DefaultReleasePage`）。share 的本机提示、help 与 MCP 给本机和被协助端的提示都是这样。官方节点和显式进程不变。

### 6.7 展示

- 协助信息里"中转服务"那一行格式不变（MCP 靠它解析）。在列表节点上时传输说明改成"TLS，证书已按节点列表校验"；地址是给协助端用的：实际连的是列表里的地址时照写（按列表里的写法），否则（本机专用地址，或 `--relay-hint` 给的不在列表里的地址）写列表里的第一个 TCP 地址（节点证书至少有一个 TCP 地址）。不在列表节点上时（显式模式、没有列表、回到默认地址）照旧。
- `official=false` 时，在下面加一行"节点运营者: <operator>（非官方节点）"。
- MCP 连上后 stderr 上那一行 `MCP: 已连接中转服务 <地址> (...)` 同样按节点说明：在列表节点上时写"TLS，证书已按节点列表校验"，地址是实际连的（这一行给本机看），第三方节点再加一行 `MCP: 节点运营者: <operator>（非官方节点）`。
- help 按码找节点的结果（`协助码属于节点 <名称>（<前缀>）`、`节点列表里没有这个协助码所属的节点，改连默认节点`）只在与上一次不同时打：MCP 每次 connect（含自动重连）都重新找。没有能用的列表、或者是 `--no-auth` 的固定码（不找节点）时清掉记录，之后同样的结果照常打。
- 命令行 help 不另打运营者一行：它不打「中转服务」那一行，连上哪个节点看 `协助码属于节点 <名称>（<前缀>）`。
- share 控制台打印选节点的结果，例如"默认节点连接失败，已改用节点 W（握手 38ms）"。

### 6.8 日志：终端输出之外默认再写一份到临时目录

现状是 share/help 只往 stdout/stderr 输出（`log` 包默认写 stderr，share 的状态提示走 `s.printf`），进程一退出或窗口关掉就没有记录；升级后的 share 是隐藏窗口启动的，更是只能靠 stdout 重定向。选节点、缓存清理这类自动行为必须事后可查，所以加默认日志文件。

- **位置**：`<os.TempDir()>/remote-assist-<uid>/<模式>-<pid>.log`，模式为 `share` / `help`。Windows 没有 uid 就用用户名（去掉域名部分，路径里不能用的字符换成 `_`）。按 PID 分文件，避免多个 share（`--new-instance`）和多个 MCP 进程互相交错，也避免 Windows 上其他进程占着文件无法轮转。`--log-file <路径>` 时就写那个文件（同样按 5 MB 轮转），不做下面的启动清理。
- **启动时打印一行**日志文件路径：`日志文件：<路径>`，各模式都打到 stderr（help 的 MCP 模式 stdout 是协议通道）。文件里第一行是版本、模式和 PID（`log` 打的版本行在打开文件之前）。
- **内容**：`log` 包的全部输出，加上 share 面向用户的状态输出（协助信息块、重连、选节点、缓存清理、传输汇总等），以及 help 面向用户的提示（stderr 上的连接、选节点、清理、P2P 提示，命令行 SSH 模式下 stdout 上的提示，失败退出时的原因）。状态输出每行前面补上与 `log` 相同格式的时间，空行不补；终端颜色控制码去掉。**不写**：MCP 的 stdout 协议流、工具请求和响应的内容、PTY 数据、文件传输内容，以及 help 端的文件传输进度行（带被协助机器上的路径）。这些里面是被协助机器上的数据。share 的工具调用摘要照写：它本来就在 share 控制台和 `log` 里，只有工具名、路径、命令名和参数个数，是本机自己的记录。
- **协助码脱敏**：协助信息块里有完整协助码，写入文件时把码替换成 `********`（复用 `logger.MaskCode`），终端上仍是完整码。实现方式是 share 持有当前码，文件写入前对内容做替换；不做"从文本里猜哪段像码"。测试用一个已知码，断言日志文件里找不到它的任何 4 字符以上片段。具体做法：share 每拿到一个码就登记（换过的旧码也留着，换码提示里新旧码都有）；help 也登记它用的码（`--code`、MCP `connect` 给的码），错误信息里可能带回来。按登记的码匹配，不分大小写，字符之间允许有 `-`、空格、`_`（展示时按 4 位分组）；不足 4 个字符的不登记，`--no-auth` 的固定码不登记。按整行替换：写到一半的行攒到换行再写，免得一个码被拆在两次写入里漏掉。
- **权限**：目录 0700、文件 0600。Linux 的 `/tmp` 所有人可写，要防别人抢先建同名目录或符号链接：用 `Lstat` 确认目录不是符号链接、属主是当前用户、权限是 0700，不满足就不写文件，只在终端警告一次，不影响运行。Windows 的临时目录本来就是每个用户自己的，只查它是真目录（不是符号链接、目录联接），不查属主和权限位。
- **体积**：单个文件到 5 MB 时轮转成 `.log.1`（只留一份）；改名失败（Windows 上被别的进程占着，多见于几个进程共用一个 `--log-file <路径>`）就清空重写，警告一次。启动时清理同目录下修改时间超过 7 天的文件，目录里最多保留 20 个文件（连同这次的，超出时先删最旧的）。只动本程序起的名字（`share-<pid>.log`、`help-<pid>.log` 和它们的 `.1`）；还在运行的进程正在写的 `.log` 不删——长时间空闲的 share 可能 7 天都没写过一行；删不掉的跳过。
- **开关**：`--log-file auto|off|<路径>`，环境变量 `REMOTE_ASSIST_LOG` 同义，命令行优先；默认 `auto`，`auto`/`off` 不分大小写。写不了文件（启动时目录不安全、打不开，或中途写失败）只在终端警告一次，之后不再写文件，不退出。
- **范围**：`remote share`、`remote help`（含 `--mcp-stdio`）。webui 起的是 `remote help --mcp-stdio` 子进程，自动覆盖。relay 不动：Linux 走 journald，Windows 走事件日志。

### 6.9 探测与黑名单计分：不加 ping 协议

核实结论见 1.2 第 10 条。**一期不新增 ping 消息**，理由如下：

1. **不需要**：测速靠的是真实建连。`prefer-default` 下只有默认节点连不上时才会并行拨其他节点，`fastest` 下只在选节点时并行一次，输的那路在握手中被取消，relay 侧记为权重 0 的 `tls_aborted` 事件，不计分。RTT 就是握手耗时，应用层 ping 得不到更多信息。
2. **有害**：新消息类型发给没升级的 relay，会按"连接前的未知消息"计 1～2 分，阈值 20。多个用户共用一个出口 IP 时，一个客户端反复探测就能把整个出口封掉。
3. **ping 风暴的实际风险并不在应用层**：真正的成本是 TLS 握手（ECDHE 加证书签名）和连接名额（单 IP 128、全局 2000）。ping 消息本身没有放大效应（TCP 握手已防伪造源地址），但也不会比握手更省。

**客户端侧的约束（防止自己变成风暴源）**：
- 同一次选节点，每个候选节点最多拨一次（TCP/QUIC 竞速除外），失败的节点 60 秒内不再拨，连续失败翻倍，最长退避到 10 分钟；随机抖动只拉长（最多 +20%），总长仍不超过 10 分钟，所以「60 秒内不再拨」是下限、10 分钟是上限，抖动都不会突破。
- 只在三个时机拨非当前节点：启动选节点、连续失败 3 次后重选、排空迁移。**不做定时测速。**
- 候选总数上限 8 个：先去掉退避期内的节点（它们不占名额），再按权重取前 8。`prefer-default`（含未知策略值）下，默认节点只要能拨就一定在内，超过 8 个时顶掉排第 8 的，因为它要被先连；`fastest` 下所有候选一视同仁，只按权重取前 8。

**relay 侧要加的保护和测试**：
- 回归测试（先 RED）：TLS 握手完成后不发消息直接断开、握手中途断开，两种情况该 IP 的封禁分都必须保持 0。这样以后有人调整计分规则时，这条会报警。
- 连接统计里这类连接会算作"扫描"，数据会有些偏差。一期规模下影响很小；以后可以把"握手后零消息"单独归类，不在本期。

**以后如果真要加 ping（二期，不在本期）必须满足**：
1. 能力声明：只对签名列表里标了 `caps: ["ping"]` 的节点发，绝不发给旧 relay 或不在列表里的 relay；
2. relay 侧单独的令牌桶（每 IP、全局），超限直接丢弃，**不计黑名单分**；
3. 响应不带任何会话或协助码信息，只含节点状态、目录序号、版本，且不大于请求；
4. 在连接统计里记为 `probe`，不记为 `scanned`。

## 7. relay 行为

- **新参数**：`--directory-url <https URL>`（开启节点模式，必须同时给 `--state-dir`）、`--directory-refresh`（默认 5m）。Windows 服务的 `config.json` 同步加 `directory_url`、`directory_refresh` 字段（`cmd/relay/service_config_windows.go`，严格解析）。**不配这两个参数时，行为和现在完全一样。**
- **拉取**：启动时先读 `<state-dir>/directory.json` 并验签，然后在后台定时拉 CF，验签、校验序号不回退、未过期后才原子写回。拉取失败就继续用旧副本，直到它过期。
- **发码**：在列表里找到自己后，生成"前缀 + 11 位随机"的码。本地查重沿用现有的 `createPendingSession` 逻辑。
- **下发列表**：Register/Join 请求新增 `directory_serial`（客户端缓存的序号，同时作为能力声明）。只有声明了这个字段、且 relay 的序号更高时，才在响应的 `directory` 字段里带上整份信封（几 KB）。share 的响应额外带 `node_status`。
- **执行状态**：

| 本节点状态 | 新客户端（声明了能力） | 旧客户端 |
|---|---|---|
| active | 正常 | 正常 |
| draining | 拒绝新注册（错误码 `NODE_DRAINING`，客户端改选其他节点）；接受凭令牌复用原码的重连，响应里带 `node_status=draining` | 正常（旧客户端不会迁移，拒绝它也没用） |
| disabled | 拒绝新注册和复用（`NODE_DISABLED`） | 拒绝，并返回中文提示"该节点已停用，请升级客户端" |

  已建立的会话不会被踢掉。
- **不新增任何列出协助码的接口**。join 失败的处理和计分不变。

## 8. Cloudflare 管理端

代码放在独立 Workers 项目的 `relay-directory/` 子目录，约定：`workers_dev = false`，只通过自定义域名访问，KV 绑定写在 `wrangler.toml`，密钥用 `wrangler secret put`，并在根 `package.json` 里加 `deploy:relay-directory` / `dev:relay-directory`。**remote-assist-tool 仓库里不放 Worker 代码、不放任何 KV id 或 secret**；它只需要知道公开地址。

- **域名（一个 Worker，两个自定义域名）**：
  - `relay-list.ifly.qzz.io`：只读公开，客户端和 relay 从这里取列表。
  - `<管理域名>`（具体子域不写进仓库）：管理页和管理 API，整个主机名放在 Cloudflare Access 后面。拆成两个主机名，是为了让 Access 策略按主机名整体生效，不用按路径写规则、也就不会因为漏了一条路径而暴露。
  - 子域名可以改，只要用自己的自定义域名，不要用 `workers.dev`。
- **路由**：
  - `relay-list`：只有 `GET /v1/directory`，只返回签名信封，`Cache-Control: max-age=60`。其他路径一律 404，且这个主机名上**没有任何写接口**。
  - `<管理域名>`：`/admin`（页面）和 `/api/*`。用 Cloudflare Access 保护（Zero Trust 免费版即可），Worker 自己还要再校验 `Cf-Access-Jwt-Assertion`（team JWKS + AUD），防止 Access 配错时裸奔。
  - **兜底（用不了 Cloudflare Access 时）**：管理端改用 secret 令牌加每 IP 限频，令牌只放在你本机。因为状态密钥只能改状态、改不了节点集合（见 3.3），令牌泄露的最坏后果也只是可用性问题。
- **KV**：
  - `nodes/<prefix>`：证书信封、状态、权重
  - `config`：策略、默认前缀
  - `status_key_cert`、`revocations`
  - `directory/current`、`directory/history/<serial>`（保留最近 50 份）
  - `audit/<ts>`：操作人邮箱、改动内容
  - 写入只发生在管理员保存时和每日定时任务，远低于免费额度。
- **保存流程**：
  1. 校验：所有根签名有效、前缀不重复、默认节点存在且为启用状态、至少有一个启用节点；
  2. 带上页面加载时的序号做乐观并发检查；
  3. 序号 +1，用状态密钥签名；
  4. 写入 current 和 history，记录审计。
- **定时任务**：每天重签一次，刷新 `expires_at`（30 天）。**每次重签（含定时任务、回滚）序号都 +1**：客户端不会用同一位置的列表替换已缓存的那份，序号不变的重签发不出去。状态密钥授权或节点证书 30 天内到期时，在页面上提醒。
- **页面功能**：
  - 节点表：前缀、名称、运营者、地址、状态、权重、证书到期日；
  - 启用、排空、停用操作。停用或排空默认节点需要二次确认，并提示"旧版客户端只会连默认节点"；
  - 策略切换（默认节点优先 / 纯最快）；
  - 上传节点证书和吊销列表（Worker 用根公钥验签后才接受）；
  - 历史和回滚：回滚是把旧内容加上新序号重新签名；
  - 审计日志。

## 9. 本地工具和节点入网流程

- `relay node-request`：放在 relay 二进制里，给节点运营者用。根据 `--cert/--key`、`--tcp/--quic` 地址、`--name/--operator/--region`，生成一份入网申请：包含证书 DER，并**用 relay 的 TLS 私钥签名**，证明申请人确实掌握这台机器。申请里没有任何秘密。换证书时加 `--prev-cert/--prev-key` 指向节点当前在用的旧证书，申请会带上旧证书并由旧私钥共签。
- `relay-admin`：新增 `cmd/relay-admin`，只在本机构建，不进 release 产物。子命令如下：
  - `keygen`：生成主、备根密钥，口令由你输入（每把至少 12 个字符，输两遍）；打印两把公钥，用于编进代码。已有密钥文件时拒绝覆盖。
  - `status-key new [--root primary|backup] [--valid 天数]`：生成状态密钥，用根密钥签授权；输出给 `wrangler secret put` 用的私钥文件（`.secret.jwk`，WebCrypto 可直接导入），以及要上传的授权。
  - `sign-node [--prefix X | --renew X] [--official] [--valid 天数] [--root primary|backup] <申请>`：先验申请签名，**再实际连一次申请里的每个 TCP/QUIC 地址，核对 relay 出示的证书指纹**；对照台账分配前缀（不指定时取第一个空闲的），设有效期（默认 365 天）和 official 标记（默认 false），打印全部内容、你输入 `yes` 后才签出节点证书。同一把 TLS 私钥不能用在两个前缀上：同一张证书挂两个前缀，两者同列时客户端整份拒绝；同一把私钥另签的证书则让持有者能同时冒充两个节点，吊销一个还会连带另一个。用 `revoke --node-serial` 点名吊销的证书，其私钥永久作废：不能再签进新证书，也不能拿来共签——吊销的是那把 TLS 私钥，节点必须换新私钥生成的证书重新申请。台账除证书指纹外还记公钥的哈希，同一把私钥另签一张证书（指纹不同）也认得出来；哈希取解析后重新编码的公钥（规范 SPKI），不取证书里的原文——同一把公钥有多种合法编码（例如改 BIT STRING 的填充位数），对原文求哈希可以被改写绕过。
  - `revoke [--node-serial N[,N...]] [--root primary|backup] [--signer primary|backup]`：签发吊销列表，自动带上以往全部吊销条目和序号下限。根密钥只能吊销主根、且必须用备用根签（默认即是）；`--root backup` 直接拒绝并提示走发版，同时列出备用根签发、发版后要改由主根处理的节点证书，台账里有吊销时还提示 `--resign`；台账里主根也已吊销时改为提示两把根都要换（见 3.3）。台账里已吊销的根不能再签任何东西，这些检查都在要口令之前。`revoke --resign [--signer primary|backup]` 不新增任何条目，只把现有的累积吊销换一把根重签（备用根发版换掉前用主根重签；含根吊销时只能用备用根签）。吊销根时按管理目录里的 `.pub` 写入公钥指纹，并把状态密钥序号下限设为当前时间：**现用的状态密钥随之作废**，要接着运行 `status-key new --root backup`，把新状态密钥和吊销列表一起上传（`status-key new` 保证新序号不低于下限，即使本机时钟回拨）。Worker 在第 4 步实现时要拒收「序号下限高于当前状态密钥序号」的吊销列表，免得发出全体客户端都拒收的列表。已吊销的根不能再吊销一次（会把下限抬到此刻、作废吊销之后新授权的状态密钥）：单独 `--root` 直接拒绝，同时带 `--node-serial` 时只吊销节点证书、下限不变。
    - 点名吊销一张证书，就是宣告它的私钥泄露：仍信任其中任一私钥的其他有效证书（换证书期间签的含新旧两个指纹的证书、同一私钥另签的证书）一并吊销，并逐条提示。否则状态密钥或 CF 账号被盗时，把那张证书重新挂上，配上泄露的私钥照样能冒充节点。被连带吊销的证书里其余的私钥不算泄露（换证书时连带吊销的那张里还有节点的新私钥，它没有泄露）。
    - 吊销主根时，先列出仍有效、由主根签发的节点证书（台账为此记下每张证书由哪把根签发；由管理目录里已经没有的旧根签的——手工换掉的旧备用根，见 3.3——也一并列出）：这份吊销生效后客户端不再接受它们。提示的下一步是：`status-key new --root backup`；按前缀逐个 `sign-node --renew X --root backup <申请>` 重签（官方节点保留 `--official`）；最后把新状态密钥、重签的节点证书和吊销列表一起上传。没重签就上传，这些节点在客户端上会全部消失。某前缀最新的证书已被吊销时不能 `--renew`（见第 9 节「只认最新那张」），改为提示吊销该前缀剩下的全部有效证书（其中另一把根签的也列出并注明客户端仍接受）、再用 `--prefix X` 重新入网。
    - 每次吊销都提示在下一个客户端版本里把条目写进 `roots.go`；含根吊销时一并打印内置状态密钥序号下限要抬到多少（见 3.3）。
  - `inspect [--builtin] <文件或 URL>`：识别节点列表、单个签名对象或入网申请，逐层验签并打印内容；第三方文本一律转义后输出。不加 `--builtin` 时用管理目录里的 `.pub`，并按台账里的吊销（节点证书、根、状态密钥序号下限）核对，结果与见过这些吊销的客户端一致；台账在但读不出来时报错，不当成没有吊销。
  - 所有签出的文件都只新建、不覆盖；台账用临时文件加改名原子写入。签出文件与台账「要么都有，要么都没有」：先写签出文件，台账写失败就删掉刚写出的文件、报「本次未签发」——台账不知道的吊销会被下一份吊销列表漏掉，台账不知道的证书会让前缀被重复分配。写台账前核对文件仍是读入时的内容，命令执行期间被另一个 relay-admin 改过或删掉就放弃写入、请你重新运行，不拿内存里的旧内容覆盖。核对证书时只做 TLS/QUIC 握手、不发任何消息，relay 不会因此给管理员 IP 计黑名单分。
- **入网流程**（自有节点和第三方节点都一样）：
  1. 节点方运行 `node-request`，把申请发给你；
  2. 你运行 `sign-node`；
  3. 在管理页上传证书，初始设为 `disabled` 或低权重；
  4. 观察没问题后启用。
- **换证书**（含证书到期续签）：**节点必须先拿到新证书、上传到 CF，再切换 TLS 证书**，否则客户端会因为指纹不符而跳过这个节点。具体顺序：
  1. 节点方用新 TLS 证书生成申请，并用 `--prev-cert/--prev-key` 让旧证书私钥共签；此时节点仍在出示旧证书；
  2. 你运行 `sign-node --renew X`：共签的旧证书必须属于前缀 X **最新签发的那张**证书，节点才可以出示它；签出含「新、旧」两个指纹的证书，在管理页替换上传；
  3. 等客户端拿到新列表后，节点切换到新 TLS 证书；
  4. 用同一份申请再运行一次 `sign-node --renew X`，签一张只含新指纹的证书并上传。
  - **为什么要共签**：节点的名称和地址都是公开的。只凭「台账里有这个前缀」就续签，任何人都能照抄这些信息、拿自己的密钥冒名换证书，把前缀指到自己的机器上。所以 `--renew` 要求申请人证明掌握该前缀**最新那张证书**的私钥：证书不变的单纯续期由申请签名本身证明，换证书由旧证书共签证明，两者都没有就拒绝。
  - **只认最新那张**：台账只追加，同前缀最后签发的那张就是「最新」。更早的证书在过期或吊销前仍然有效、仍占着前缀，但它们的私钥不能再用来续签——可能留在退役机器或旧备份里。最新那张被吊销时，`--renew` 一律拒绝、不退回去认更早的一张（哪把旧私钥都可能已泄露），要先吊销同前缀其余仍有效的证书，再走 `--prefix X`。
  - 续签时名称、运营者或地址有变化会单独提示（地址列出新旧对照）：前缀挪到别的地址是最需要看清的变化。官方节点续签没带 `--official` 也会单独提示新证书不再是官方节点。
  - 旧私钥确实丢了：先 `revoke --node-serial` 吊销该前缀全部仍有效的证书，前缀随之空出，再按新节点 `--prefix X` 签发（等于重新入网，要你人工确认对方身份）。
  - 列表里每个前缀只能放一张证书，上传新证书就替换了旧的，所以正常换证书不必吊销旧证书；只有怀疑旧 TLS 私钥泄露时才 `revoke --node-serial` 吊销旧证书序号。

## 10. 兼容性

| share | help | 结果 |
|---|---|---|
| 旧 | 旧 | 不变，都在默认节点 |
| 旧（在默认节点） | 新 | 协助信息带 server 时直连；只有码时按前缀路由，路由错了回退到默认节点 |
| 新（自动） | 旧，走 MCP | 协助信息带 server，能跟过去（前提是 help 机器能连上该节点） |
| 新（自动） | 旧 CLI 只给码，或 webui 留空 | 默认节点优先策略下，share 只要连得上默认节点就在默认节点，能用；share 因连不上默认节点而落到别的节点时，连不上（这种情况今天本来就完全不可用） |
| 新 | 新 | 能用 |
| 任意 | 任意，连未配置 `--directory-url` 的自建 relay | 完全不变 |
| 新客户端 | 旧 relay | relay 忽略新字段、不下发列表；列表来自 CF 或缓存 |

**已知限制（写进发布说明）**：旧版本的通道内升级总是往新进程的命令行里写 `--server <当时连的地址>`。所以由旧版本通道内升级出来的 share，再升到新版后仍是显式模式（6.1：写了 `--server` 就算显式，写的是内置地址也算），之后的链式升级也一直保持显式：不按列表选节点，节点排空、下线时不会迁移。用户重启一次 share（或机器重启后由自启项按原始命令行拉起）就进入自动模式。不在升级参数里自动把 `--server <内置地址>` 改成 `--relay-hint`：那样会把用户自己写的 `--server <内置地址>` 也当成自动模式，和 6.1 冲突。

- 日志文件：
  - 用一个已知协助码跑一遍 share 注册流程，日志文件里不得出现该码的任何 4 字符以上片段，终端输出里仍是完整码；
  - help 的 `--mcp-stdio` 下，stdout 只有协议数据，日志路径只打到 stderr，工具响应内容不进文件；
  - 目录权限不对（符号链接、属主不是当前用户、权限过宽）时不写文件、只警告一次；
  - 轮转到 5 MB、启动清理超过 7 天的旧文件、目录内最多 20 个；
  - `--log-file off` 和 `REMOTE_ASSIST_LOG=off` 都能关闭，写失败不影响运行。
- relay 计分回归（先 RED）：TLS 握手完成后不发消息就断开、握手中途断开，该 IP 的封禁分保持 0。
- e2e：
  - 本机起两台 relay，使用测试根密钥，验证 share 自动选节点、help 只给码也能连；
  - 参照 `legacy_compat_e2e_test.go`，用旧二进制交叉测试兼容性。
- 本机验证遵循已知约束：CRLF 签出不能全仓 gofmt；本机缺 gcc，跑不了 `-race`；clipboard 相关测试受环境影响不稳定。

## 12. 实现拆分和上线顺序

**实现**（每一步都单独 review）：
1. `internal/directory`（格式、验签、缓存）和 `cmd/relay-admin`；
2. relay 节点模式；
3. 客户端选节点和路由；
4. CF Worker 和管理页；
5. e2e 测试和文档。

**上线**：
1. 你在本机运行 `relay-admin keygen`，自己输口令；公钥提交进代码。
2. 部署 CF 端：在 Workers 项目的 `relay-directory/` 里部署 Worker、建 KV、配 Access，需要有 Worker、KV 和 Access 写权限的 Cloudflare 凭据。部署和改 Access 都会改线上配置，我执行前会先给你看改动。然后运行 `status-key new`，再 `wrangler secret put`。
3. 两台 relay 各自运行 `node-request`，你签发证书，上传 CF；默认节点设为海外那台。
4. relay 升级并加上 `--directory-url`：沿用"空闲时升级、先备份、准备 rollback"的流程，**每台都单独征得你同意**。
5. 发布客户端新版本。
6. 观察旧版 help 的占比，降下来后在管理页切到"纯最快"。
