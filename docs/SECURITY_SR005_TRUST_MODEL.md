# SR-005：工具通道信任模型设计与决策文档

## 1. 文档目的

本文对应风险评估中的 SR-005（当前工具通道加密不能抵抗恶意或失陷的 Relay），是一份供安全评审和架构决策使用的可评审工程文档。

SR-005 的状态为 **OPEN，需要架构决策**。本文不直接改代码，目标是把两条整改路线（选项 A：信任 Relay；选项 B：端到端不信任 Relay）的改造范围、工作量、残留风险和推荐结论写清楚，供评审会拍板；决策落定后再进入实现阶段。

本文同时纳入一条在 SR-005 复核中新识别、与信任模型直接相关的威胁：**ClientID 作为长期可转发的重连凭据**（见第 6 节），并给出与 SR-009（操作员绑定）合并处理的建议。

## 2. 现状与问题复述

### 2.1 密钥派生现状

工具通道会话密钥由以下方式派生（`internal/proto/handshake.go:33-42`）：

```
key = HKDF-SHA256(
        ikm  = code,
        salt = nonceShare + "|" + nonceHelp,
        info = "rat-tool-v" + ToolProtocolVersion)
```

在此密钥之上，工具载荷使用 XChaCha20-Poly1305 AEAD 加解密（`internal/proto/aead.go`）。

### 2.2 关键事实

- 协助码 `code` 由 **Relay 生成**（`internal/relay/server.go:341` 调用 `s.codes.Generate()`），并保存在 Relay 会话状态中，当前还会进入日志（SR-004）。
- `ToolHello` / `ToolHelloAck` 携带双方 nonce，由 **Relay 解析外层消息并转发**（`internal/proto/handshake.go`、`internal/client/help_mcp.go:34-52`、`internal/client/share.go:690-706`、`internal/relay/server.go:307-310`）。
- 因此，**密钥派生的三项输入（code、nonceShare、nonceHelp）在 Relay 侧全部可见**。

### 2.3 安全影响

- 当前 AEAD 能阻止 Relay 的普通转发逻辑直接读取明文工具载荷，也能检测随机篡改。
- 但控制 Relay 进程的攻击者可以拿到全部密钥派生输入，**自行推导会话密钥**，从而：
  - 解密工具请求与响应，读取被协助终端上的文件、日志、凭据；
  - 伪造工具请求，在被协助终端上执行任意命令；
  - 冒充 Help 或 Share，接管会话。
- 换言之：**当前实现无法提供"Relay 失陷后仍保持端到端机密性与真实性"的保证**。产品文档中若存在"Relay 被攻破也看不见、无法伪造"的表述，与实现不符，必须修正（无论最终选 A 还是 B）。

## 3. 选项 A：将 Relay 明确定义为可信安全边界

### 3.1 思路

不改变现有密码学结构，转而在**制度和运维层面**把 Relay 声明为可信数据边界：接受"Relay 失陷即可影响活动会话"这一事实，通过主机加固、最小权限、审计和正式风险审批把风险控制在可接受范围内。

### 3.2 改造范围

- **文档与产品描述修正**：删除或修正一切"Relay 被攻破也无法解密/伪造"的表述，改为"Relay 是可信边界，Relay 失陷可读取和伪造活动会话工具数据"。更新威胁模型（`docs/SECURITY_RISK_ASSESSMENT.md` 4.3 信任决策）。
- **独立主机部署**：使用独立、无其他业务数据的 Relay 云主机（与 SR-007 混部整改协同）。
- **主机加固**：严格 systemd 沙箱（`NoNewPrivileges`、`ProtectSystem=strict`、`ProtectHome`、`PrivateTmp`、能力/设备/资源边界）、最小权限服务账号、及时补丁、集中审计与监控。
- **风险接受流程**：由安全负责人对"Relay 失陷影响活动会话"完成书面风险接受。

### 3.3 工作量

- 代码改动：几乎为零（仅文档字符串、能力描述、可能的启动横幅措辞）。
- 运维改动：中等，主要落在部署拓扑、systemd 单元、监控告警和审批流程，多数与 SR-007/SR-008 的整改重叠。
- 密码学评审：不需要新协议评审。

估算：**以文档和运维为主，约 1-2 人日代码/文档工作 + 部署加固（与其他 SR 合并计算）**。

### 3.4 残留风险

- Relay 主机或进程一旦失陷，攻击者可在会话有效期内解密、伪造、接管会话，读取终端文件并执行命令。这是**被明确接受**的残留风险，而非被消除的风险。
- 日志平台、Relay 低权限账号、同机 root 业务（SR-007）任一失陷都可能间接触达会话密钥材料。
- 安全性完全依赖运维纪律，长期看比密码学保证更脆弱。

### 3.5 适用场景

Relay 由己方严格管控、且能接受"信任边界=Relay"这一前提的部署；作为**首期上线的现实选择**成本最低。

## 4. 选项 B：实现真正不信任 Relay 的端到端协议

### 4.1 思路

让 Relay 只做**定位和转发**，不再持有可推导会话密钥的完整秘密。会话密钥由 Share/Help 两端通过经过评审的密钥协商协议直接协商，Relay 观察到的全部流量都不足以计算出会话密钥。

核心原则（对应风险评估 SR-005 选项 B）：

- **协助秘密由 Share 本地生成，Relay 不得获得完整秘密**：把当前"Relay 生成 code 并派生密钥"的模型，改为"Relay 只持有公开定位 ID / 验证器，不持有认证秘密"。
- **公开会话定位 ID 与秘密认证材料分离**：Relay 用定位 ID 路由，认证材料只在两端之间校验。
- **使用经评审的协议，不自行拼装密码学**：二选一：
  - **PAKE**（如 CPace / OPAQUE 类）：适合"两端共享一个短口令（协助码），要在不泄露口令、抗离线爆破的前提下协商强密钥"的场景。协助码继续作为人工交换的短口令，但 Relay 看到的握手消息无法用于离线猜测口令或推导密钥。
  - **Noise / X25519**：适合"用长期或临时公钥做认证密钥交换"的场景。需要额外的身份/公钥分发与绑定机制（例如通过 DMS 下发对端公钥或指纹），否则中间的 Relay 可做 MITM。
- **会话密钥必须绑定完整上下文**：绑定双方身份、协议版本、会话 ID 和**完整握手 transcript**，防止降级和拼接攻击。
- **Relay 只保存定位信息或验证器**，不能根据观察到的流量计算会话密钥。

### 4.2 改造范围

- **握手协议重写**：`internal/proto/handshake.go` 的 `DeriveSessionKey` 及 `ToolHello`/`ToolHelloAck` 交换流程需替换为选定的 PAKE 或 Noise 握手；`internal/proto/aead.go` 的 AEAD 原语可复用，但密钥来源改变。
- **Relay 转发路径调整**：`internal/relay/server.go` 中解析并转发握手消息的逻辑，改为对握手报文**不透明转发**（Relay 不再需要理解 nonce 语义），并将 code 的角色从"密钥输入"降级为"定位/验证器"。
- **协助码语义变更**：code 不再由 Relay 派生密钥用（PAKE 下作为口令，Noise 下可能仅作定位/人工核对因子）。
- **身份绑定基础设施**（Noise 路线）：需要公钥/指纹的可信分发通道（很可能依赖 DMS，与 SR-009 强相关）。
- **协议版本与降级防护**：新增版本协商与 transcript 绑定，需覆盖旧客户端兼容或强制升级策略。
- **客户端两端同步升级**：Share 与 Help 必须同版本，涉及平滑升级与灰度。

### 4.3 工作量

- 代码改动：**大**。涉及握手协议、Relay 转发、客户端两端、版本兼容和测试。
- 密码学评审：**必须**。需要独立密码学评审 + 协议级测试（含恶意 Relay 测试向量），不能以"单元测试通过"代替安全证明。
- 依赖引入：需要引入经评审的 PAKE / Noise 库并锁定版本，评估供应链风险。

估算：**多人周量级**，且关键路径在密码学评审与协议测试，而非纯编码。

### 4.4 残留风险

- 若身份绑定（尤其 Noise 路线的公钥分发）设计不当，恶意 Relay 仍可做 MITM——**端到端安全的强度取决于身份绑定的可信根**，而非协议本身。
- 自行拼装或误用协议（错误的 transcript 绑定、nonce 复用、降级未防护）会引入比现状更隐蔽的漏洞，因此**独立密码学评审是硬性前置**。
- 协议复杂度上升带来实现与维护成本，长期需要专人维护。

### 4.5 适用场景

对"Relay 不可信 / 多方托管 / 合规要求端到端机密性"的部署；是**长期正确方向**，但不适合作为首期上线的唯一阻塞项。

## 5. 推荐

分阶段推进，避免用一个多人周的密码学工程阻塞公网上线：

1. **首期（现在）：采用选项 A**，把 Relay 明确声明为可信边界，同步修正产品/威胁模型描述，并完成书面风险接受。这是成本最低、可立即闭环 SR-005 状态的现实路径，前提是与 SR-007（独立主机/混部）、SR-008（后端链路）、SR-004（协助码脱敏）的整改协同到位。
2. **中长期：规划选项 B**，优先评估 **PAKE** 路线（协助码天然是短口令，PAKE 能在不引入额外公钥分发基础设施的前提下抗离线爆破、且让 Relay 无法推导密钥）；Noise/X25519 作为需要强身份绑定时的备选，但必须先解决公钥可信分发（很可能借道 DMS，与 SR-009 合并）。选项 B 立项时必须把"独立密码学评审 + 恶意 Relay 协议测试"列为验收前置。

无论选 A 还是 B，**都必须先修正文档中不准确的安全能力描述**——这是 SR-005 验收标准的第一条。

## 6. 关联威胁：ClientID 作为长期可转发重连凭据

### 6.1 问题

复核 SR-005 时发现，Share 的 **ClientID 目前是一枚长期、可转发的会话重连凭据**，与"信任模型/身份绑定"直接相关，应与 SR-005/SR-009 一并处理。

事实依据：

- ClientID 是本地持久化的 128 bit 随机值，落盘在用户主目录 `~/.remote_assist_client_id`（`0600`），**长期不变、无过期、无吊销**（`internal/client/clientid.go`）。
- Share 注册时携带 ClientID；Relay 一旦按 ClientID 查到现有会话，就**复用该会话及其协助码**并把 Share 换绑到新连接（`internal/relay/server.go:322-332` → `GetSessionByClientID` / `ReuseSession`）。
- 该复用**只凭 ClientID 匹配**，不校验其它身份因子。
- ClientID 目前还会以**完整明文写入日志**（`internal/relay/server.go:330` 的 `Reusing existing session for client %s`）。

### 6.2 威胁

- **凭据转发/窃取即接管**：任何拿到某 Share ClientID 的一方（读到落盘文件、抓到注册报文、或从 Relay 日志中读到），都能冒充该 Share 发起注册，**复用其活动会话并取得当前协助码**，进而把会话导向攻击者掌控的连接。
- **长期有效放大风险**：ClientID 不过期、不可吊销，一次泄露即长期可用；这与协助码 30 分钟有效期的设计意图相悖。
- **日志留存放大暴露面**：完整 ClientID 入日志后，日志平台/备份链路失陷即等价于凭据泄露（与 SR-004 协助码入日志同类问题）。

### 6.3 建议

- **重连令牌与身份分离**：引入**独立的、可过期、可吊销的重连令牌**（server 签发、绑定会话/设备、短有效期），用于会话复用；ClientID 退回为纯粹的本地设备标识，不再单独作为复用授权凭据。
- **禁止完整 ClientID 入日志**：与 SR-004 协助码脱敏一致，日志只记录不可逆指纹（带服务端审计密钥的 HMAC 截断值）或固定长度掩码，禁止 `%s` 打印完整 ClientID。
- **与 SR-009 合并议定**：ClientID 复用授权应纳入 SR-009 的操作员/设备绑定框架——由 DMS 签发的短期、一次性、带签名票据统一承载"谁、在哪台设备、哪次会话"的授权，重连令牌在该框架下签发与校验，避免出现"绕过协助码但凭长期 ClientID 直接接管"的旁路。

### 6.4 验收要点（供 SR-009 合并评审时细化）

- 泄露/复制他人 ClientID 后，在无有效重连令牌的情况下不能复用会话、不能取得协助码。
- 重连令牌可设置有效期并可主动吊销；过期或被吊销后复用失败。
- 全仓搜索及端到端日志采集均不能找到完整 ClientID。
