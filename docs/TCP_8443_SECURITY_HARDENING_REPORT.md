# Remote Assist Relay TCP 8443 安全与鉴权加固评估报告

文档日期：2026-07-23
评估对象：`remote-assist-tool` Relay
代码基线：`e8273e3`（核心加固提交：`c60d28a`）
申请范围：入站 **TCP 8443**
明确不在本次申请范围：UDP 3478、HTTP/HTTPS Web 服务、Relay 主机管理端口

## 1. 审批摘要

### 1.1 结论

建议对 TCP 8443 采取**有条件开放**：在第 7 节强制部署条件全部落实、并完成第 9 节上线验证后，可以开放该端口供 Remote Assist 的 Share/Help 客户端连接。

本结论不是对任意配置的无条件放行。下列任一情况存在时，不建议开放到公网：

- Relay 使用 `--plain`，或未能证明 8443 实际提供 TLS 1.3。
- Share/Help 使用默认的 `--insecure=true`，未校验 Relay 证书和域名。
- Relay 或客户端启用 `--no-auth`。
- 未限制 UDP/P2P，导致实际通信面超出本次 TCP 8443 审批范围。
- 无法接受“协助码是当前主要应用鉴权凭据、尚未绑定企业操作员身份”的残余风险。
- 无法接受“Relay 是可信安全边界，Relay 失陷可影响活动会话”的残余风险。

### 1.2 安全属性概览

| 项目 | 当前能力 | 审批判断 |
|---|---|---|
| 传输加密 | 服务端最低 TLS 1.3 | 满足，但必须显式部署正式证书 |
| Relay 身份认证 | 客户端可校验证书链和域名 | 满足，但 CLI 当前默认跳过校验，生产必须覆盖 |
| 客户端 TLS 身份 | 未实现 mTLS | 不具备 |
| Help 应用鉴权 | 默认 10 位随机协助码，30 分钟有效 | 具备短期 bearer 鉴权 |
| 企业操作员身份/MFA/工单绑定 | 未实现 | 残余风险，需接受或继续整改 |
| 在线爆破防护 | per-IP、全局、单连接三层限制 | 已加固 |
| 资源耗尽防护 | 连接、会话、消息、速率、超时均有限制 | 已加固 |
| 审计 | 连接、协助码生成、Join 拒绝、会话建立/关闭 | 已具备，需接入集中监控 |
| 协助码日志保护 | 仅记录 96 bit HMAC 指纹，不记录明文码 | 已加固 |
| UDP 入口 | 默认关闭内置 STUN | 本次保持关闭 |

## 2. 服务与网络边界

### 2.1 数据流

```text
Share 客户端                           Help 客户端
    |                                     |
    | 出站 TCP/TLS 1.3                    | 出站 TCP/TLS 1.3
    +------------------+  +---------------+
                       v  v
                 Relay TCP 8443
             会话登记、鉴权、配对与转发
```

- Share 和 Help 均主动向 Relay 建立出站连接；终端侧不需要开放入站 8443。
- Relay 8443 使用自定义的换行分隔 JSON 消息协议，是**裸 TCP/TLS 服务，不是 HTTP 服务**。
- Web WAF、HTTP Header 鉴权和 HTTP 路由规则不适用于该端口；应使用四层负载均衡、安全组、网络 ACL 或主机防火墙。
- 本次建议 Share/Help 固定使用 `--p2p disabled`，所有业务流量均通过已审批的 TCP 8443 转发。

### 2.2 Relay 权限边界

Relay 进程只进行会话登记、地址协商和消息转发，不在 Relay 主机执行远程工具命令。命令执行和文件访问发生在主动运行 `remote share` 的被协助终端上。

但是，成功取得协助码的 Help 可在 Share 端授权范围内执行命令、读写文件。因此该端口承载的是高影响远程协助能力，协助码泄露和 Share 进程权限必须按高敏感凭据与高权限进程管理。

## 3. 鉴权模型

### 3.1 分阶段鉴权

| 阶段 | 校验机制 | 未通过时行为 |
|---|---|---|
| TCP 建连 | 安全组/防火墙、连接数上限 | 超限直接关闭 |
| TLS 握手 | TLS 1.3；客户端应校验证书链和域名 | 握手失败，不进入业务协议 |
| Share 注册 | 无操作员身份；允许客户端申请新会话 | 受注册速率和会话总量限制 |
| Help 加入 | 提交协助码，Relay 查验存在性、TTL、Share 状态和占用状态 | 返回统一 `join failed`，不泄露失败原因 |
| 会话使用 | 连接状态机、Share/Help 配对和数据消息限流 | 越权消息关闭或丢弃 |
| 工具通道 | 协助码和双方随机 nonce 派生密钥，XChaCha20-Poly1305 AEAD | 密文校验失败则拒绝 |

### 3.2 协助码强度

- 使用 `crypto/rand` 生成，不依赖时间戳或伪随机种子。
- 默认字符集 54 个字符，长度 10，理论空间为 `54^10`，约 57.55 bit 熵。
- 默认 TTL 为 30 分钟。
- 同一会话同时最多允许一个 Help。
- 协助码允许为了人工输入移除 `-`、空格和 `_` 后再比较，但不进行大小写折叠。
- 协助码属于 bearer credential：任何持有码者都可在有效期内尝试加入，不能证明其企业账号、岗位或工单身份。

### 3.3 爆破与枚举防护

默认限制如下，均可通过受校验的 JSON 配置文件覆盖：

| 控制项 | 默认值 |
|---|---:|
| 单 IP Join 速率 / burst | 5/s / 20 |
| 全局 Join 速率 / burst | 200/s / 400 |
| 单连接连续 Join 失败上限 | 5 |
| 单 IP 注册速率 / burst | 2/s / 10 |
| 全局注册速率 / burst | 100/s / 200 |

所有 Join 失败对外返回相同错误，避免根据“无效、过期、已占用”等不同响应枚举有效协助码。内部原因只进入受采样保护的审计日志。

## 4. 8443 现有安全控制

### 4.1 传输层

- Relay 端 `tls.Config.MinVersion` 为 TLS 1.3。
- 客户端同样要求最低 TLS 1.3。
- 使用正式 CA 证书且客户端设置 `--insecure=false` 时，由 Go TLS 栈验证证书链和连接域名。
- TLS 私钥文件应由服务账号独占读取；项目生成自签名私钥时权限为 `0600`，但自动生成证书只包含 `localhost/127.0.0.1`，不适合公网域名。

注意：Go 的 TLS 1.3 密码套件由运行时安全策略管理，代码中的 `CipherSuites` 字段不用于限定 TLS 1.3 套件。因此审批应以实际端口扫描结果为准，不应仅根据源码中的套件列表下结论。

### 4.2 协议状态机

- 每条连接只能执行一次 Register 或一次成功 Join。
- 未完成 Register/Join 前发送隧道、心跳、工具或 P2P 控制消息会被判为协议错误。
- 未知消息、畸形 Register/Join payload 会关闭连接。
- Help 换代、Share 重连和断连时会重置数据面状态，避免旧连接继续占用会话。

### 4.3 容量与慢速攻击防护

| 控制项 | 默认值/行为 |
|---|---:|
| 全局 TCP 并发连接 | 2000 |
| 单来源 IP 并发连接 | 128 |
| 全局活跃会话 | 5000 |
| 单来源 IP 活跃会话 | 10 |
| 单消息大小 | 4 MiB |
| 读空闲超时 | 2 分钟 |
| 单次写超时 | 30 秒 |
| TCP KeepAlive | 30 秒 |
| 单连接数据消息速率 / burst | 100/s / 200 |
| 全局数据消息速率 / burst | 5000/s / 10000 |

这些限制覆盖连接耗尽、会话耗尽、slowloris、慢读写、超大消息和高频消息洪水。配置加载拒绝未知字段、非正数和尾随 JSON，避免拼写错误或零值意外关闭安全控制。

### 4.4 审计与凭据保护

- 审计文件创建权限为 `0600`。
- 记录连接、协助码生成、会话建立/关闭及 Join 拒绝原因。
- 协助码不写入普通日志或审计日志；日志使用进程内随机密钥生成的 96 bit HMAC 指纹关联同一码的事件。
- 高频拒绝日志按可配置间隔采样，包含累计计数，降低日志 I/O 放大风险。
- 审计 HMAC 密钥只存在内存，进程重启后轮换。

## 6. 重要残余风险

### R1：协助码不是企业身份凭据

当前 Help 鉴权只证明“持有协助码”，不证明操作员是谁，也没有 MFA、DMS/SSO 票据、工单号或目标设备绑定。若安全制度要求每次远程操作可归因到企业账号，应在开放前增加 mTLS 客户端证书或服务端校验的短期签名操作员票据；否则需由安全负责人书面接受该风险。

### R2：Relay 是可信安全边界

工具密钥由协助码和两端 nonce 派生，而这些输入在 Relay 侧均可见。XChaCha20-Poly1305 能防随机篡改，但不能保证恶意或已失陷 Relay 无法推导密钥、解密或伪造活动会话。当前首期部署必须把 Relay 作为可信边界，使用独立主机、最小权限和集中监控；若合规要求 Relay 不可见业务内容，需要另行实现经独立密码学评审的 PAKE/Noise 类端到端协议。

### R3：TLS 存在配置型 fail-open 路径

`cmd/relay` 未显式指定证书时会尝试自动生成自签名证书；若证书目录创建或生成失败，当前启动路径可能因证书路径为空而退回普通 TCP 监听。生产部署必须显式传入 `--cert` 和 `--key`，并在开放安全组前探测 8443 实际协议。建议后续代码整改为：只要 `UseTLS=true`，证书缺失或加载失败就终止启动，禁止回退明文。

### R4：客户端默认跳过证书校验

Share/Help 的 `--insecure` 当前默认值为 `true`，原因是兼容内置自签名证书。公网生产环境必须由部署脚本、配置平台或启动参数显式设置 `--insecure=false`；仅“服务端开启 TLS”不能替代客户端身份校验。

### R5：Share 注册入口不验证操作员

任意能连接 8443 的客户端均可注册自己的 Share 会话，但不能因此访问其他 Share。资源限流能够限制滥用规模，但若需要禁止非受管终端注册，仍需增加设备身份或上游网络准入。

### R6：协助码过期不强制中止已建立会话

TTL 控制新的 Help 加入。Share 和 Help 已配对且仍保持活动时，超过协助码 TTL 后会话可以继续，直到一端断开或空闲超时。审批时应把 TTL 理解为“加入窗口”，不是“最长远程操作时长”；需要最长会话时长时应另加策略。

### R7：ClientID 具有会话复用授权语义

Share 的持久 ClientID 可用于复用原会话。当前日志已只记录其指纹，复用过程也已原子化，但 ClientID 本身仍是长期本地凭据，尚无服务端过期和吊销机制。应保护客户端本地 ClientID 文件；中长期建议拆分短期可吊销的重连令牌。

### R8：审计初始化失败不会阻止服务启动

审计文件初始化失败当前只记录 Warning。生产启动和监控必须检查审计文件可写、事件持续产生并能被集中采集；建议后续增加生产模式下审计失败即停止启动的选项。

## 7. 强制部署基线

以下条件建议作为 8443 防火墙审批单的附加约束。

### 7.1 Relay 启动

示例：

```powershell
relay.exe `
  --listen ':8443' `
  --cert 'D:\relay\certs\relay.example.com.crt' `
  --key 'D:\relay\certs\relay.example.com.key' `
  --ttl '30m' `
  --length '10' `
  --plain=false `
  --no-auth=false `
  --stun='' `
  --trust-source-ip=true `
  --audit 'D:\relay\logs\audit.log' `
  --limits-file 'D:\relay\config\limits.json'
```

要求：

1. 使用受信 CA 签发、SAN 包含实际访问域名、处于有效期内的证书。
2. 显式传入 `--cert` 和 `--key`；私钥 ACL 仅允许 Relay 服务账号和受控管理员读取。
3. 禁止 `--plain` 和 `--no-auth`。
4. `--stun=''`，防火墙不开放 UDP 3478。
5. 配置文件纳入版本管理/配置中心审批，启动日志保存完整生效阈值。
6. Relay 使用独立低权限服务账号运行，不授予交互登录、管理员/root 或访问业务数据的权限。

### 7.2 客户端启动

```powershell
remote.exe share `
  --server 'relay.example.com:8443' `
  --insecure=false `
  --p2p disabled `
  --root 'D:\approved-workspace' `
  --allow-exec 'git,go,powershell.exe'

remote.exe help `
  --server 'relay.example.com:8443' `
  --insecure=false `
  --p2p disabled `
  --code '<协助码>'
```

要求：

1. 生产启动模板必须显式包含 `--insecure=false` 和 `--p2p disabled`。
2. 不使用 `--unsafe-exec`；按业务最小集设置 `--allow-exec`。
3. 使用 `--root` 限制文件工具目录，但不能把该参数视为命令执行安全边界；Share 应运行在专用低权限账号、容器或受控终端环境中。
4. 协助码通过受控即时通信、工单或带访问控制的短时渠道传递，不写入群公告、普通日志、截图库或长期配置。

### 7.3 网络策略

1. 优先只允许公司 VPN、堡垒机或固定办公出口 IP 访问 TCP 8443。
2. 若业务确需 `0.0.0.0/0`，必须启用云侧 DDoS/四层连接防护，并书面接受“协助码是主要应用鉴权”的风险。
3. 仅开放 TCP 8443；拒绝 UDP 3478 和其他未审批端口。
4. 优先使用四层 TCP 透传，让 TLS 在 Relay 终止并保留真实源 IP。
5. 若负载均衡对后端执行 SNAT，Relay 使用 `--trust-source-ip=false`，同时由负载均衡/云防火墙承担真实源 IP 的连接、速率和封禁控制。
6. 若在负载均衡终止 TLS，后端端口必须只允许负载均衡安全组访问；更推荐 TLS 重加密或四层透传，避免后端明文信任边界。

### 7.4 审计与监控

至少监控：

- TCP 新建连接、活跃连接和拒绝率。
- TLS 握手失败、证书到期时间和非 TLS 访问。
- `join_rejected` 的 `reason`、`sample_total` 和来源 IP。
- `rate_limited_global`、连接总量、会话总量和写超时。
- Relay 进程退出、重启、审计日志停止增长和配置变化。
- 单 IP 在短时间内尝试大量不同 `code_fp` 的枚举特征。

| 源 IP 行为 | Relay 或上游能按真实源 IP 计费 |
| 日志搜索 | 不存在完整协助码和完整持久 ClientID |
| 审计可用性 | 连接、Join 拒绝、建立和关闭事件可检索并告警 |
| 进程权限 | Relay 服务账号无管理员/root 和业务目录访问权限 |
| 实际启动参数 | 不含 `--plain`、`--no-auth`、客户端不含 `--insecure=true` |

可使用以下工具进行部署侧验证：

```text
openssl s_client -connect relay.example.com:8443 -tls1_2
openssl s_client -connect relay.example.com:8443 -tls1_3 -servername relay.example.com -verify_return_error
nmap -sT -sV -p 8443 relay.example.com
nmap -sU -p 3478 relay.example.com
```

## 10. 应急处置与回滚

发生异常连接激增、协助码泄露、Relay 主机疑似失陷或审计中断时：

1. 在安全组/防火墙撤销 TCP 8443 入站规则，或缩小到应急处置来源 IP。
2. 停止 Relay 服务；进程重启会清空内存会话、协助码和审计指纹密钥。
3. 保全 Relay 日志、云防火墙/LB 日志和主机审计，避免先清理后取证。
4. 轮换 TLS 私钥和证书；检查服务账号、二进制和配置文件完整性。
5. 通知所有 Share 终止会话并重新生成协助码。
6. 完成原因分析、凭据轮换和安全复核后再恢复规则。

## 11. 审批建议

### 可批准条件

- 第 7 节强制部署基线全部落实。
- 第 9.2 节部署验证全部通过并留存证据。
- 安全部门接受短期协助码 bearer 鉴权及可信 Relay 模型，或已增加企业操作员身份校验。
- 首期只开放 TCP 8443，UDP 3478 保持关闭。

### 应拒绝或暂缓条件

- 使用明文 TCP、默认自签名证书配合 `--insecure=true`，或无法证明证书校验生效。
- 启用 `--no-auth` 或 `--unsafe-exec`。
- 要求企业身份可追溯，但没有 mTLS/SSO/DMS 票据或书面风险接受。
- Relay 与高价值业务混部、使用管理员/root 运行，或审计不可用。
- 实际流量还包含 UDP/P2P，但审批范围只覆盖 TCP 8443。

## 12. 后续加固路线

建议按优先级推进：

1. TLS fail closed：`UseTLS=true` 时证书缺失或加载失败必须退出。
2. 将生产客户端默认改为证书校验，或提供不可覆盖的企业部署策略。
3. 增加 DMS/SSO 短期签名票据或 mTLS，把操作员、目标设备、工单和有效期绑定到 Join。
4. 将持久 ClientID 与短期、可过期、可吊销的重连令牌分离。
5. 增加最大会话时长和服务端主动吊销能力。
6. 若要求 Relay 不可信，采用成熟 PAKE/Noise 库并进行独立密码学评审。
7. 增加生产模式下审计初始化失败即停止服务的选项。
